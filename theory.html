Unit I: Architecture, Data Independence & ER Modeling

Q1. What is Data Independency in DBMS? Explain Logical vs Physical data independence.

Data Independence is the capacity to alter a schema definition at one level of the three-schema database system without requiring alterations to the schema definition at the next higher level. It isolates applications from physical storage reorganizations and logical schema refactoring.

  1. Logical Data Independence: The ability to modify the conceptual schema (e.g., adding or removing attributes, creating new relationships, or splitting an entity table) without altering external schemas (user views) or existing application programs.
    • Example: Adding a new column Aadhar_No or splitting an Employee table into Emp_Personal and Emp_Salary can be shielded from users by defining a view that joins the two tables back together.
  2. Physical Data Independence: The ability to modify the internal/physical storage schema (e.g., creating B+ tree indexes, reorganizing sequential file clusters, migrating to SSD partitions) without altering the conceptual schema or application code.
    • Example: Building a hash cluster index on Student(Roll_No) accelerates query execution time from O(N) to O(1) without requiring any changes to user SQL queries.

Note: Logical data independence is significantly harder to achieve than physical data independence because application logic is tightly coupled to the structure of conceptual relations.

Q2. Define the evolution of database systems from file systems to modern architectures.

Database management architectures have evolved over several distinct historical generations:

  1. Flat-File Processing (1960s): Application-specific operating system files. Suffered from severe data redundancy, inconsistency, tight program-data coupling, and zero concurrent write isolation.
  2. Hierarchical Data Model (Late 1960s, IBM IMS): Tree-structured hierarchy where records are organized as parent-child nodes (1:N relationships) navigated through rigid physical disk pointers.
  3. Network Data Model (1970s, CODASYL DBTG): Graph-based network where child records can possess multiple parent records (M:N relationships), traversed via complex pointer arrays.
  4. Relational Model (1970, Dr. E.F. Codd, IBM System R): Two-dimensional relations (tables) with rows (tuples) and columns (attributes), manipulated declaratively using relational algebra and standardized SQL without exposing physical access paths.
  5. Object-Oriented & Object-Relational (1990s): Supported encapsulation, complex inheritance, multimedia data types, and stored user-defined methods alongside relational tables.
  6. NoSQL & NewSQL (2000s–Present): Distributed document stores (MongoDB), key-value stores (Redis), columnar stores (Cassandra), and horizontally scalable ACID relational engines (Google Spanner, CockroachDB).

Q3. Why are Network and Hierarchical Data models rarely used today compared to Relational models?

Hierarchical and Network systems have been largely superseded by the Relational Model (RDBMS) due to critical architectural limitations:

Q4. Define Aggregation in ER modeling with a concrete example.

Aggregation is an ER abstraction that treats an entire relationship set (along with its participating entity sets) as a single higher-level composite entity set, enabling it to participate in further relationships with other entity sets.

Why it is needed: An ER relationship cannot directly connect to another relationship. Aggregation overcomes this limitation by wrapping a relationship into an entity container.

Concrete Example:

  • Consider entity sets Employee, Project, and the ternary or binary relationship Works_On(Employee, Project).
  • Suppose the enterprise requires specialized machinery for each specific project assignment. We cannot connect Machinery to the relationship Works_On directly.
  • Solution: Aggregate Works_On(Employee, Project) into a higher-level composite entity [Assignment], which then participates in a binary relationship Requires([Assignment], Machinery).

Q5. Name any five widely-used database management systems and their architectural characteristics.

  1. Oracle Database (Oracle Corp): Leading commercial enterprise RDBMS supporting multi-tenant pluggable databases (PDB), advanced PL/SQL engines, and Real Application Clusters (RAC).
  2. PostgreSQL (PostgreSQL Global Dev Group): Leading open-source object-relational database renowned for strict SQL compliance, extensible types, foreign data wrappers (FDW), and MVCC.
  3. MySQL (Oracle Corp): Popular open-source web RDBMS utilizing pluggable storage engines (InnoDB for ACID transactions, MyISAM for read-heavy workloads).
  4. Microsoft SQL Server (Microsoft): Enterprise RDBMS integrated with Windows ecosystems, featuring T-SQL, columnstore indexing, and Always On availability groups.
  5. SQLite (D. Richard Hipp / Public Domain): Zero-configuration, serverless, self-contained, transactional SQL engine embedded directly into mobile apps and embedded devices.

Q6. What is the significance of Physical Data Independence? Give an example.

Physical Data Independence permits database administrators to modify physical storage organizations, file clustering methods, and indexing structures to optimize I/O performance without forcing modifications to conceptual schemas, external views, or application queries.

Concrete Demonstration:

  • Consider an e-commerce relation Orders(Order_ID, Customer_ID, Order_Date, Amount).
  • Initially, records are stored as an unordered heap file. As query volume surges, the DBA builds a secondary B+ tree index on Order_Date and reorganizes table partitions by year across separate NVMe disks.
  • Significance: The application program SELECT * FROM Orders WHERE Order_Date = '2025-01-01' requires zero code rewrites, zero recompilations, and zero downtime. The query optimizer automatically leverages the new index transparently.

Q7. List and explain the primary functions of a Database Administrator (DBA).

The Database Administrator (DBA) is the centralized authority responsible for the operational integrity, performance, and governance of the enterprise database:

  1. Schema Definition & Storage Architecture: Translates conceptual business requirements into physical and logical DDL schemas, allocating disk storage spaces and table clusters.
  2. Security & Privilege Management: Regulates user authorization, manages authentication credentials, defines role-based access control (RBAC), and monitors audit logs to prevent data breaches.
  3. Performance Monitoring & Tuning: Analyzes query execution plans, configures RAM buffer pools, monitors disk I/O bottlenecks, and designs secondary indexes to ensure SLA compliance.
  4. Backup & Disaster Recovery: Implements comprehensive backup schedules (full, differential, transaction log) and conducts recovery drills to restore system state after catastrophic failures.
  5. Integrity Constraint Enforcement: Declares and maintains domain, primary key, foreign key referential integrity, and business assertion rules.

Q8. When is a relationship set called a recursive (self-referencing) relationship set? Provide an example.

A relationship set is called Recursive (or self-referencing) when the same entity set participates more than once in the relationship set in distinct structural roles.

Example & Role Names:

  • Consider the entity set Employee and the relationship Manages.
  • Both the manager and the subordinate are instances of the Employee entity set.
  • To distinguish the participating entities, explicit Role Indicators are assigned:
    • Employee in the role of Supervisor / Manager (1).
    • Employee in the role of Subordinate / Supervisee (N).
  • Relational Table Representation:
    EMPLOYEE(Emp_ID, Name, Salary, Manager_Emp_ID)
    where Manager_Emp_ID is a foreign key referencing Emp_ID within the very same table.

Q10. List four major disadvantages of the traditional file processing system over DBMS.

  1. Data Redundancy and Inconsistency: Multiple application programs maintain their own redundant copies of the same data records. Modifying one file without updating other copies causes contradictory database states.
  2. Difficulty in Accessing Data: Ad-hoc queries require developing brand-new bespoke programs in C or COBOL rather than executing declarative ad-hoc queries (like SQL).
  3. Data Isolation and Atomicity Problems: Data is scattered across incompatible proprietary file formats. If a transaction crashes mid-operation, the file system cannot roll back changes, violating Atomicity.
  4. Lack of Concurrent Access Control: OS file locks are coarse-grained (entire file locked), leading to severe thread contention, dirty reads, and lost updates during simultaneous user access.

Q11. Explain Logical Data Independence and discuss why it is more difficult to achieve than physical independence.

Logical Data Independence shields user applications from structural alterations in the conceptual schema (such as vertical or horizontal relation splitting, or attribute expansion).

Why it is significantly more difficult to achieve:

  1. Application programs embed business queries that explicitly name relations and attribute columns. If a relation is split horizontally or vertically, application queries referencing the original relation will fail unless comprehensive external views and update-triggers (INSTEAD OF) are engineered.
  2. In contrast, physical storage changes (such as creating a B+ tree index or changing disk block sizes) do not alter the table names, attribute types, or query semantics—the query optimizer automatically adjusts physical access paths.

Q12. What are the key advantages of using a Database Management System (DBMS)?

  1. Self-Describing Nature: Maintains a centralized system catalog (Data Dictionary) that stores metadata definitions independently of application code.
  2. Program-Data Independence: Separates logical data definitions from low-level storage layouts.
  3. Controlling Data Redundancy: Eliminates uncontrolled duplication through normalization, enforcing a single source of truth.
  4. ACID Transaction Support: Guarantees Atomicity, Consistency, Isolation, and Durability in the presence of concurrent access and hardware crashes.
  5. Multi-User Concurrency Control: Employs locking and timestamp protocols to interleave operations safely without data corruption.
  6. Standardized Declarative Querying: Provides ANSI SQL for expressive, high-level data definition and manipulation.

Q13. What is the concept of Keys in databases? Differentiate Superkey, Candidate Key, and Primary Key.

A Key is an attribute or set of attributes used to uniquely identify individual tuples within a relation instance.

  1. Superkey (SK): Any set of attributes for which no two distinct tuples in any valid relation state can have the identical values:
    ∀ t₁, t₂ ∈ r(R), t₁ ≠ t₂ ⇒ t₁[SK] ≠ t₂[SK].
  2. Candidate Key (CK): A minimal Superkey—a superkey from which no attribute can be removed without destroying the uniqueness property. A relation may possess multiple candidate keys.
  3. Primary Key (PK): The specific Candidate Key chosen by the database designer as the principal mechanism for identifying tuples within the relation. Primary Key attributes are strictly prohibited from holding NULL values (Entity Integrity).

Q14. What are Strong and Weak Entity Sets? Explain the concept of Discriminator (Partial Key).

  1. Strong Entity Set: An entity set that possesses a distinct Primary Key comprised entirely of its own attributes. Its existence does not depend on any other entity set. Depicted by a single rectangle.
  2. Weak Entity Set: An entity set that does not possess sufficient attributes to form a Primary Key of its own. It is existence-dependent on an identifying (owner) strong entity set. Depicted by a double rectangle.
    • Identifying Relationship: The relationship associating a weak entity set with its owner. Depicted by a double diamond.
    • Partial Key (Discriminator): The set of attributes within a weak entity set that uniquely identifies instances among all entities dependent on the same owner entity. Depicted by a dashed underline.
    • Primary Key Formulation: The Primary Key of a weak entity set is formed by combining the Primary Key of its owner entity with its own Partial Key:
      PK(Weak) = PK(Owner) ∪ Partial_Key(Weak).

Q15. Explain Specialization, Generalization, and Attribute Inheritance in Extended ER (EER).

  1. Generalization (Bottom-Up): The process of extracting common attributes and relationships from multiple lower-level entity sets to synthesize a generalized, higher-level superclass entity set (e.g., combining Car and Truck into Vehicle).
  2. Specialization (Top-Down): The process of defining distinctive, lower-level subclass entity sets from a generalized superclass entity set based on specific distinguishing characteristics (e.g., specializing Employee into Salaried_Employee and Hourly_Employee).
  3. Attribute & Relationship Inheritance: A crucial rule of EER modeling where every entity instance belonging to a subclass automatically inherits all attributes and relationship participations of its parent superclass, in addition to its own specific attributes.
  4. Constraints on Specialization:
    • Disjointness Constraint: Disjoint [d] (subclasses are mutually exclusive) vs Overlapping [o] (an entity can belong to multiple subclasses).
    • Completeness Constraint: Total (=) (every superclass entity must belong to a subclass) vs Partial (-) (an entity may belong to none).

Q17. What are the different types of Relational Integrity Constraints?

Integrity Constraints are declarative predicates enforced by the DBMS to guarantee that database modifications do not result in semantic inconsistency or data corruption:

  1. Domain Constraint: Specifies that every attribute value must be an atomic element belonging to its declared domain type, range, or enumerated set (e.g., CHECK(Salary > 0)).
  2. Key Constraint (Uniqueness): Mandates that candidate key attributes must uniquely identify every tuple:
    ∀ t₁, t₂ ∈ r(R), t₁ ≠ t₂ ⇒ t₁[CK] ≠ t₂[CK].
  3. Entity Integrity Constraint: Mandates that no attribute participating in the Primary Key of a base relation can contain a NULL value:
    ∀ t ∈ r(R), t[PK] ≠ NULL.
  4. Referential Integrity Constraint: Enforces consistency across relationships by requiring that foreign key values in a referencing (child) relation must match an existing primary key value in the referenced (parent) relation, or be entirely NULL:
    FK ∈ r₁(R₁) ⊆ πPK(r₂(R₂)).

Q18. Explain the 5 command families of SQL (DDL, DML, DQL, DCL, TCL) with syntax examples.

  1. DDL (Data Definition Language): Specifies schema creation and alteration.
    CREATE TABLE Student(Roll_No INT PRIMARY KEY, Name VARCHAR(50));
  2. DML (Data Manipulation Language): Modifies table instance records.
    INSERT INTO Student VALUES(101, 'Alice'); UPDATE Student SET Name='Alice J' WHERE Roll_No=101;
  3. DQL (Data Query Language): Queries declarative data sets.
    SELECT Roll_No, Name FROM Student WHERE Roll_No > 100 ORDER BY Name;
  4. DCL (Data Control Language): Regulates user privileges and security permissions.
    GRANT SELECT, INSERT ON Student TO faculty_user; REVOKE INSERT ON Student FROM faculty_user;
  5. TCL (Transaction Control Language): Regulates ACID transactional boundaries.
    SAVEPOINT sp1; UPDATE Accounts SET Bal = Bal - 100; COMMIT;

Q19. What are the fundamental and derived Relational Algebra operations?

Relational algebra operations are divided into primitive (fundamental) and derived operators:

  1. Fundamental Operators:
    • Selection (σp(R)): Filters tuples satisfying boolean predicate p.
    • Projection (πL(R)): Extracts specified attribute columns L and eliminates duplicate tuples.
    • Cartesian Product (R × S): Combines each tuple in relation R with every tuple in relation S.
    • Set Union (R ∪ S): Combines tuples from union-compatible relations.
    • Set Difference (R - S): Returns tuples present in R that are absent in S.
    • Rename (ρS(R)): Assigns a new relation or attribute identifier.
  2. Derived Operators:
    • Set Intersection (R ∩ S = R - (R - S)): Returns common tuples.
    • Theta Join (R ⋈θ S = σθ(R × S)): Cross-product filtered by join condition.
    • Natural Join (R ⋈ S): Equijoin over identically named common attributes with duplicate column suppression.
    • Division (R ÷ S): Solves universal quantification ("find entities associated with ALL items in S").

Q20. What is Relational Calculus? Differentiate between TRC and DRC.

Relational Calculus is a formal non-procedural (declarative) query language based on first-order predicate logic. A query describes what information is desired without specifying the procedural evaluation algorithm.

Q21. What is an Equi-Join and how does it differ from Natural Join?

  1. Equi-Join: A Theta Join where the predicate condition uses strictly the equality operator (=):
    R ⋈R.A = S.B S.
    Key Attribute: Both join columns R.A and S.B are retained in the output schema, resulting in duplicate column values.
  2. Natural Join (R ⋈ S): A specialized equijoin that automatically matches all attributes sharing identical names between relations R and S, automatically eliminating duplicate common columns.
    Example: If EMP(Emp_ID, Name, Dept_ID) and DEPT(Dept_ID, DName) are joined, Natural Join outputs (Emp_ID, Name, Dept_ID, DName) containing only one Dept_ID column.

Q22. What is a CLAUSE in terms of SQL? Explain WHERE, HAVING, GROUP BY, and ORDER BY.

A Clause in SQL is a structural component of an SQL statement that specifies data filtering, aggregation, grouping, or ordering criteria:

  1. WHERE Clause: Filters individual candidate rows before any grouping or aggregation takes place.
    SELECT * FROM Emp WHERE Salary > 50000;
  2. GROUP BY Clause: Collapses rows sharing identical values in specified columns into summary groups for aggregate evaluation (COUNT, SUM, AVG).
    SELECT Dept_ID, AVG(Salary) FROM Emp GROUP BY Dept_ID;
  3. HAVING Clause: Filters summary groups produced by the GROUP BY clause after aggregate computation (cannot be performed by WHERE).
    SELECT Dept_ID, COUNT(*) FROM Emp GROUP BY Dept_ID HAVING COUNT(*) > 10;
  4. ORDER BY Clause: Sorts the final result set in ascending (ASC) or descending (DESC) sequence.
    SELECT * FROM Emp ORDER BY Salary DESC, Name ASC;

Q24. Define Relational Algebra and its significance as a procedural query language.

Relational Algebra is a formal mathematical query language in which queries are expressed as procedural expressions consisting of relational operators applied to relation instances. It is closed—every operation on relations produces a new relation.

Significance in DBMS Engines:

  1. When a user submits a declarative SQL query, the DBMS SQL parser translates the SQL into an internal Relational Algebra Query Tree.
  2. The DBMS Query Optimizer applies algebraic equivalence transformations (such as pushing selections and projections down the tree) to minimize intermediate relation sizes and select the lowest-cost execution plan.

Q25. Explain the safety of relational calculus expressions and the domain restriction rule.

In Relational Calculus, an expression may theoretically evaluate to an infinite relation if not properly constrained. An expression is defined as Safe if it is guaranteed to produce a finite result set that is a subset of the domain of values present in the database or the query formula itself.

Example of an Unsafe Expression:

{ t | eg(t ∈ ext{Student}) }

This query specifies all tuples t in the universe that are NOT in Student, resulting in an infinite number of non-database tuples. The Domain of a Formula (dom(ψ)) ensures safety by restricting quantified variables to values explicitly present in the input relations or explicit constants.

Q26. What are Views in SQL? Explain the WITH CHECK OPTION clause.

A View is a virtual relation defined by an underlying stored SQL query. It does not store physical tuples on disk (unless materialized); instead, the DBMS reconstructs view data on demand by merging the view query with the user's outer query.

WITH CHECK OPTION:

  • Ensures that all INSERT and UPDATE operations executed against an updatable view satisfy the selection condition in the view definition.
  • Example: 
    CREATE VIEW CSE_Students AS
                            SELECT Roll_No, Name, Dept FROM Student
                            WHERE Dept = 'CSE'
                            WITH CHECK OPTION;
    Attempting to insert a row with Dept = 'ECE' through CSE_Students will be rejected with an integrity constraint violation.

Q27. Explain the different types of Joins in SQL.

  1. INNER JOIN: Returns only matching rows where the join predicate evaluates to true in both tables.
    SELECT * FROM Emp E INNER JOIN Dept D ON E.Dept_ID = D.Dept_ID;
  2. LEFT OUTER JOIN: Returns all rows from the left table; unmatched rows from the right table are padded with NULL values.
  3. RIGHT OUTER JOIN: Returns all rows from the right table; unmatched rows from the left table are padded with NULL values.
  4. FULL OUTER JOIN: Returns all rows from both tables, preserving unmatched rows from both sides padded with NULL values.
  5. CROSS JOIN (Cartesian Product): Produces the cross product of every row in the first table with every row in the second table (M imes N rows).

Q28. Define Triggers and explain their types in SQL/PL-SQL.

A Trigger is a stored procedural program in the database catalog that executes automatically ("fires") in response to a specified DDL or DML event (INSERT, UPDATE, DELETE) on a table or view.

  1. Timing:
    • BEFORE: Fires prior to executing the triggering DML statement (ideal for input validation and sanitization).
    • AFTER: Fires following successful DML execution (ideal for audit logging and cascading state changes).
    • INSTEAD OF: Fires in place of the triggering statement (enables DML updates on complex non-updatable views).
  2. Granularity:
    • Row-Level Trigger (FOR EACH ROW): Fires once for every individual row affected by the DML statement. Accesses pseudo-records :OLD and :NEW.
    • Statement-Level Trigger: Fires exactly once for the entire DML statement, regardless of how many rows are modified.

Q29. What are PL/SQL Cursors? Differentiate between Implicit and Explicit cursors.

A Cursor is a private work area allocated in memory by the DBMS to manage the context and result set of a multi-row SQL query.

  1. Implicit Cursors: Automatically declared and managed by the database engine whenever an individual DML statement (INSERT, UPDATE, DELETE, or single-row SELECT INTO) is executed. Accessed via attributes: SQL%FOUND, SQL%NOTFOUND, SQL%ROWCOUNT.
  2. Explicit Cursors: Programmatically defined and controlled by the developer for multi-row result sets. Follows a strict lifecycle:
    • DECLARE: Defines the cursor query.
    • OPEN: Allocates memory and evaluates the active query result set.
    • FETCH: Retrieves the current row into variables and advances the internal pointer.
    • CLOSE: Releases private work area resources.

Q30. Explain the concept of B+ Tree Indexing in relational database storage.

A B+ Tree is a balanced search tree data structure optimized for secondary disk block storage, ensuring that all leaf nodes reside at the exact same depth. It serves as the default indexing structure in enterprise databases (PostgreSQL, Oracle, MySQL InnoDB).

  1. Internal Nodes: Act as index routing pointers containing search keys and disk block pointers, without holding actual tuple data.
  2. Leaf Nodes: Hold all search keys alongside physical record pointers (RID) or entire clustered data rows. Crucially, all leaf nodes are linked sequentially via a doubly-linked list.
  3. Search Performance: Point queries (WHERE ID = 500) execute in O(logB N) disk I/O operations. Range queries (WHERE Age BETWEEN 20 AND 30) find the start key in O(logB N) time and traverse the linked list directly, avoiding tree traversals.

Unit III: Relational Database Design & Normalization

Q31. What are the advantages of database normalization?

Database Normalization is the theoretical process of decomposing relations with anomalies to produce smaller, well-structured relations. Key benefits:

  1. Elimination of Data Modification Anomalies:
    • Insertion Anomaly: Inability to represent an independent fact without adding an unrelated entity record (e.g., cannot add a new course until a student enrolls).
    • Deletion Anomaly: Loss of critical business facts as an unintended side-effect of deleting an unrelated tuple (e.g., deleting the last student enrolled in a department inadvertently wipes the department's existence).
    • Update Anomaly: Data inconsistency resulting from updating redundant records in some rows while missing others.
  2. Minimization of Storage Redundancy: Eliminates duplicate attribute occurrences across tuples, significantly optimizing disk and memory buffer utilization.
  3. Lossless Join Guarantee: Decompositions ensure the original relation can be reconstructed without producing spurious or phantom tuples.
  4. Dependency Preservation: Ensures that all business constraints (FDs) can be verified by inspecting individual tables without performing expensive multi-table joins.

Q32. What are the Inference Rules for Functional Dependencies (Armstrong's Axioms)?

Armstrong's Axioms form a complete and sound set of inference rules used to compute the closure of functional dependencies (F⁺):

  1. Primary Axioms:
    • Reflexivity Rule: If Y ⊂eq X, then X → Y. (Trivial dependency).
    • Augmentation Rule: If X → Y, then XZ → YZ for any attribute set Z.
    • Transitivity Rule: If X → Y and Y → Z, then X → Z.
  2. Secondary (Derived) Rules:
    • Union Rule: If X → Y and X → Z, then X → YZ.
    • Decomposition Rule: If X → YZ, then X → Y and X → Z.
    • Pseudo-transitivity Rule: If X → Y and γ Y → Z, then γ X → Z.

Q33. What is Boyce-Codd Normal Form (BCNF) in DBMS? State the condition.

A relation schema R is in Boyce-Codd Normal Form (BCNF) if and only if, for every non-trivial functional dependency X o A that holds on R, the determinant attribute set X is a Superkey of R.

Key Properties of BCNF:

  1. BCNF strictly eliminates all redundancy arising from functional dependencies.
  2. Every relation in BCNF is guaranteed to be in 3NF, 2NF, and 1NF (BCNF ⊆ 3NF ⊆ 2NF ⊆ 1NF).
  3. Trade-off: Unlike 3NF, BCNF decomposition guarantees Lossless Join reconstruction, but does not always preserve functional dependencies.

Q34. Define the Closure of an Attribute Set and explain its algorithm.

The Closure of an Attribute Set X (denoted X⁺) under a set of functional dependencies F is the set of all attributes functionally determined by X under F.

Algorithm to Compute X⁺:

  1. Initialize X⁺ = X.
  2. Repeat until X⁺ does not change:
    • For each FD Y o Z in F:
    • If Y ⊂eq X⁺, then X⁺ = X⁺ ∪ Z.
  3. Return X⁺.

Usefulness: If X⁺ contains all attributes of relation schema R, then X is a Superkey. If no proper subset of X derives all attributes, X is a Candidate Key.

Q36. Explain Multivalued Dependency (MVD) with a suitable example.

A Multivalued Dependency X woheadrightarrow Y holds on schema R(X, Y, Z) if the set of values of Y associated with a given X-value is completely independent of the values of Z.

Formal Definition: For any two tuples t₁, t₂ ∈ r with t₁[X] = t₂[X], there must exist tuples t₃, t₄ such that:
t₃[X] = t₄[X] = t₁[X], t₃[Y] = t₁[Y], t₃[Z] = t₂[Z], and t₄[Y] = t₂[Y], t₄[Z] = t₁[Z].

Concrete Example: Consider relation Instructor(Emp_ID, Phone_No, Skill). An instructor has multiple phone numbers and multiple skills independently. Storing this in a single table requires Cartesian explosion of redundant tuples. 4NF decomposes this into (Emp_ID, Phone_No) and (Emp_ID, Skill).

Q37. What are Transitive Dependencies? Explain the anomalies they cause.

In a relation schema R, a functional dependency X o Z is Transitive if there exists an attribute set Y such that X o Y and Y o Z hold, where Y ot o X (i.e. Y is not a candidate key) and Z ot⊂eq Y.

Example: In Employee(Emp_ID, Dept_ID, Dept_Name):
Emp_ID → Dept_ID and Dept_ID → Dept_Name. Thus, Emp_ID → Dept_Name is transitive.

Anomalies Caused:

  1. Update Anomaly: Changing the department name requires updating all employee records working in that department.
  2. Insertion Anomaly: Cannot register a newly created department until an employee is assigned to it.
  3. Deletion Anomaly: Deleting the last employee in a department permanently erases the department's name from the system.

Q38. Define Third Normal Form (3NF) and state its conditions.

A relation schema R is in Third Normal Form (3NF) if it is in 2NF and, for every non-trivial functional dependency X o A holding on R, at least ONE of the following conditions is satisfied:

  1. X is a Superkey of R (same as BCNF condition), OR
  2. A is a Prime Attribute (i.e., A is a member of some candidate key of R).

Advantage over BCNF: Any relation schema can always be decomposed into 3NF relations such that the decomposition is simultaneously Lossless Join AND Dependency Preserving (via Bernstein's 3NF synthesis algorithm).

Q39. Define First Normal Form (1NF) and Second Normal Form (2NF) with examples.

  1. First Normal Form (1NF): Mandates that the domain of all attributes must contain only atomic (indivisible) scalar values, prohibiting repeating groups, arrays, and nested relations.
    Violation: Student(Roll_No, Name, Subjects) where Subjects = 'Math, DBMS, OS' violates 1NF.
    Fix: Separate each subject into its own individual tuple.
  2. Second Normal Form (2NF): A relation is in 2NF if it is in 1NF and no non-prime attribute is partially dependent on any candidate key of the relation.
    Violation: In Enroll(Student_ID, Course_ID, Student_Name, Grade), candidate key is {Student_ID, Course_ID}. Since Student_ID → Student_Name, the non-prime attribute Student_Name depends only on a proper subset of the key.
    Fix: Decompose into Student(Student_ID, Student_Name) and Enroll(Student_ID, Course_ID, Grade).

Q40. What is a Minimal Cover (Canonical Cover) of a set of functional dependencies?

A Minimal Cover (Canonical Cover) Fc of a set of functional dependencies F is an equivalent simplified set of FDs (Fc ≡ F) that contains no extraneous attributes and no redundant dependencies.

Three Mandatory Properties of Fc:

  1. Standard (Singleton) RHS: Every dependency in Fc has a single attribute on its right-hand side (X o A).
  2. No Extraneous Attributes: No attribute can be deleted from the left-hand side of any dependency without altering the closure (F⁺).
  3. No Redundant Dependencies: No dependency can be removed from Fc without reducing the closure ((Fc - {X o A})⁺ e F⁺).

Q41. What is Lossless Join Decomposition? State the necessary and sufficient condition.

A decomposition of relation schema R into subschemas R₁, R₂ is a Lossless Join Decomposition with respect to dependency set F if, for every valid instance r(R):

πR₁(r) owtie πR₂(r) = r

Necessary and Sufficient Condition:

For a binary decomposition into R₁ and R₂, the decomposition is lossless if and only if the intersection of their attribute sets forms a superkey of at least one of the decomposed schemas:

(R₁ ∩ R₂) o R₁ ∈ F⁺   ext{OR}   (R₁ ∩ R₂) o R₂ ∈ F⁺

Q42. What is Dependency Preservation in schema decomposition?

A decomposition of relation schema R into R₁, R₂, …, Rₖ with dependency set F is Dependency Preserving if the union of the projections of F onto each subschema logically implies all dependencies in F:

(F₁ ∪ F₂ ∪ … ∪ Fₖ)⁺ = F⁺

Practical Value: When a database update occurs on table Rᵢ, the DBMS can verify that all declared functional dependencies remain satisfied by inspecting only table Rᵢ locally, without having to perform an expensive multi-table join across all decomposed relations.

Q44. Define Fourth Normal Form (4NF) and explain how it addresses Multivalued Dependencies.

A relation schema R is in Fourth Normal Form (4NF) if and only if, for every non-trivial multivalued dependency X woheadrightarrow Y holding on R, the determinant X is a Superkey of R.

  1. Trivial MVD: An MVD X woheadrightarrow Y is trivial if Y ⊂eq X or X ∪ Y = R.
  2. Significance: 4NF eliminates independent 1:M relationships coexisting in the same table, preventing combinatorial record explosion.

Q45. Define Fifth Normal Form (5NF / Project-Join Normal Form) and Join Dependencies.

A relation schema R is in Fifth Normal Form (5NF) (or Project-Join Normal Form, PJNF) if every non-trivial Join Dependency owtie(R₁, R₂, …, Rₙ) holding on R is implied by the candidate keys of R.

  1. Join Dependency: A relation satisfies join dependency owtie(R₁, R₂, …, Rₙ) if R can be losslessly decomposed into and reconstructed from n ≥ 3 sub-relations without spurious tuples.
  2. 5NF guarantees that a relation cannot be further non-loss decomposed into smaller relations without losing data consistency.

Unit IV: Transaction Processing, Serializability & Recovery

Q46. What is a Transaction in DBMS? Explain ACID properties with banking examples.

A Transaction is a logical unit of database processing that includes one or more database access operations (read, write, update, delete). It transforms the database from one consistent state to another consistent state.

To ensure database integrity, every transaction must strictly satisfy the ACID Properties:

  1. Atomicity ("All or Nothing"): Guarantees that either all operations of the transaction complete successfully, or none of them have any effect on the database. If a failure occurs midway, all partial modifications must be rolled back.
    Banking Example: Transferring $500 from Account A to Account B requires deducting $500 from A and adding $500 to B. If the system crashes after deducting from A, Atomicity ensures the $500 deduction is undone.
  2. Consistency (Preservation of Invariants): Ensures that the execution of a transaction in isolation preserves all explicit schema constraints, domain rules, and semantic database invariants.
    Banking Example: The sum total of balances in accounts A and B before the transfer must equal the sum total after the transfer (Anew + Bnew = Aold + Bold).
  3. Isolation (Independent Execution): Guarantees that the intermediate states of concurrently executing transactions are invisible to one another. Each transaction behaves as if it were the sole transaction executing on the database.
    Banking Example: While transaction $T_1$ transfers money between A and B, concurrent transaction $T_2$ calculating the branch total cannot see A deducted before B is credited.
  4. Durability (Persistence of Committed Updates): Guarantees that once a transaction completes and commits, its state modifications persist permanently in non-volatile storage, surviving subsequent power outages or operating system crashes.
    Banking Example: Once a customer receives a "Transfer Successful" confirmation receipt, the updated balances remain permanently recorded even if the server crashes seconds later.

Q47. Draw and explain the Transaction State Diagram (Active to Terminated).

During its execution lifecycle, a transaction transitions through several distinct operational states:

  1. Active: The initial state upon creation where the transaction begins executing its read and write operations.
  2. Partially Committed: The state reached immediately after the final statement has completed execution, but before the log records are flushed to non-volatile disk.
  3. Committed: Reached after all updates and transaction log records are successfully flushed to disk. The transaction has permanently terminated with success.
  4. Failed: Entered when regular execution can no longer proceed due to hardware errors, logical exceptions, or integrity constraint violations.
  5. Aborted: Entered after the transaction is rolled back and the database state is restored to its pre-transaction state. The transaction manager can restart or terminate the transaction.
  6. Terminated: The final exit point after commit or abort, where all memory buffers and transaction locks are released back to the system.

Q48. What is a Schedule? Differentiate between Serial, Non-Serial, and Concurrent Schedules.

A Schedule (or History) is an ordered chronological sequence of operations (read, write, abort, commit) from a set of concurrent transactions that preserves the individual operation order within each transaction.

Q49. Define Conflict Serializability and explain the Conflicting Operations condition.

A schedule $S$ is Conflict Serializable if it can be transformed into a serial schedule by a series of swaps of non-conflicting adjacent operations.

Conditions for Two Operations to Conflict: Two operations $O_i$ and $O_j$ in a schedule are said to be in conflict if and only if they satisfy all three of the following criteria:

  1. They belong to different transactions ($T_i \ne T_j$).
  2. They access the exact same data item (e.g., item $X$).
  3. At least one of the two operations is a Write operation:
    • Read-Write Conflict: $R_i(X)$ and $W_j(X)$ (leads to unrepeatable reads or inconsistent analysis).
    • Write-Read Conflict: $W_i(X)$ and $R_j(X)$ (leads to reading uncommitted dirty data).
    • Write-Write Conflict: $W_i(X)$ and $W_j(X)$ (leads to lost updates or overwritten data).

Note: Two read operations $R_i(X)$ and $R_j(X)$ do not conflict because reading does not mutate data state.

Q50. How is a Precedence Graph (Serialization Graph) constructed to test conflict serializability?

A Precedence Graph (or Conflict / Serialization Graph) is a directed graph $G = (V, E)$ used to determine whether a concurrent schedule is conflict serializable:

  1. Vertices ($V$): Create a node for each active transaction participating in the schedule ($T_1, T_2, \dots, T_n$).
  2. Directed Edges ($E$): Draw a directed edge from $T_i → T_j$ if an operation of $T_i$ precedes and conflicts with an operation of $T_j$ on some data item $X$:
    • $T_i$ executes $R(X)$ before $T_j$ executes $W(X)$.
    • $T_i$ executes $W(X)$ before $T_j$ executes $R(X)$.
    • $T_i$ executes $W(X)$ before $T_j$ executes $W(X)$.
  3. Serializability Theorem: A schedule $S$ is conflict serializable if and only if its precedence graph contains NO directed cycles.
    If acyclic, the topological sort of the graph yields the equivalent serial ordering of transactions.

Q51. What is View Serializability? Explain the three conditions of View Equivalence and Blind Writes.

A schedule $S$ is View Serializable if it is view equivalent to some serial schedule $S_{serial}$ consisting of the same participating transactions.

Three Rules for View Equivalence: Two schedules $S$ and $S'$ over the same transactions are view equivalent if:

  1. Initial Read: For each data item $X$, if transaction $T_i$ reads the initial value of $X$ in $S$, then $T_i$ must also read the initial value of $X$ in $S'$.
  2. Updated Read (Read-From): If transaction $T_i$ reads a value of $X$ written by transaction $T_j$ in $S$, then $T_i$ must also read the value of $X$ written by $T_j$ in $S'$.
  3. Final Write: For each data item $X$, if transaction $T_i$ performs the final write on $X$ in $S$, then $T_i$ must perform the final write on $X$ in $S'$.

Blind Writes: A write operation $W_i(X)$ executed without a prior $R_i(X)$ by the same transaction is called a blind write. View serializable schedules that are not conflict serializable always contain blind writes.

Q52. Explain Recoverable Schedules, Cascading Aborts, and Cascadeless Schedules.

In concurrent processing, transaction rollbacks can trigger chain reactions across other transactions unless properly restricted:

  1. Recoverable Schedule: A schedule where, for every pair of transactions $T_i$ and $T_j$, if $T_j$ reads a data item previously written by $T_i$, then the commit operation of $T_i$ must precede the commit operation of $T_j$ (Cᵢ < Cⱼ). Prevents committed transactions from having read uncommitted rolled-back data.
  2. Cascading Rollback (Cascading Abort): A phenomenon where the failure and rollback of one transaction ($T_1$) forces the recursive abort and rollback of multiple dependent transactions ($T_2, T_3, \dots$) that read uncommitted data written by $T_1$. Leads to massive wasted CPU and I/O work.
  3. Cascadeless Schedule (Avoids Cascading Aborts - ACA): A schedule where every transaction is permitted to read a data item $X$ only after the previous transaction that wrote $X$ has committed (Wᵢ(X) … Cᵢ … Rⱼ(X)).
    Hierarchy: Strict Schedules ⊆ Cascadeless Schedules ⊆ Recoverable Schedules.

Q53. What is a Strict Schedule and why is it desirable in practical database engines?

A schedule is Strict if a transaction is not allowed to read or write a data item $X$ until the previous transaction that wrote $X$ has either committed or aborted:

∀ Tᵢ, Tⱼ: Wᵢ(X) ⇒ (Cᵢ ∨ Aᵢ) precedes both Rⱼ(X) and Wⱼ(X)

Why Strict Schedules are Desirable in DBMS:

  1. Trivial Rollback Recovery: If an active transaction $T_1$ fails, the DBMS restores the before-image of modified items from the undo log without accidentally overwriting uncommitted or committed updates of concurrent transactions.
  2. Zero Cascading Aborts: Dependent transactions never read dirty uncommitted values.
  3. Implemented via Strict 2PL: Enforced in commercial DBMSs (PostgreSQL, MySQL InnoDB, SQL Server) by holding all exclusive locks until transaction completion (COMMIT or ROLLBACK).

Q54. Explain Log-Based Recovery and Write-Ahead Logging (WAL) protocol.

The Write-Ahead Logging (WAL) protocol is the foundational mechanism ensuring the Atomicity and Durability (ACID) of transactions across unexpected system failures.

  1. Log Record Structure: Every database mutation is appended sequentially to an append-only log file before altering disk data pages:
    <T_id, DataItem, Old_Value (Before-Image), New_Value (After-Image)>
  2. Core WAL Rules:
    • Undo Rule: The log record containing the before-image must be flushed to non-volatile disk before the corresponding dirty data page is written from memory to disk. (Enables rollback).
    • Redo Rule: All log records for a transaction (including the <COMMIT> record) must be flushed to non-volatile disk before the transaction is acknowledged as committed to the client. (Enables crash replay).

Q56. What is a Checkpoint in database recovery and how does it reduce recovery crash replay overhead?

A Checkpoint is an administrative operation performed periodically by the DBMS recovery manager to flush in-memory buffers to stable storage, limiting the amount of log that must be scanned during crash recovery.

  1. Checkpoint Sequence:
    • Stop accepting new transactions temporarily (or use fuzzy checkpointing).
    • Flush all modified database buffer pool pages (dirty pages) from RAM to non-volatile disk storage.
    • Append a <CHECKPOINT L> record to the log, where $L$ is the list of transactions active at checkpoint time.
    • Flush all log records up to the checkpoint record to stable disk storage.
  2. Crash Recovery Benefit: The recovery system does not need to scan the entire log file from the beginning of database creation. It only needs to scan backward to the most recent checkpoint record, dramatically speeding up recovery time.

Q57. Explain Deadlock in DBMS and the 4 necessary Coffman conditions for deadlock occurrence.

A Deadlock is an execution impasse where two or more transactions are in a simultaneous circular wait state, each waiting to acquire a lock on a resource held by another transaction in the cycle.

Deadlocks can occur only if all 4 Coffman Conditions hold simultaneously:

  1. Mutual Exclusion: At least one resource (table, page, tuple) must be held in a non-shareable exclusive mode (Exclusive lock).
  2. Hold and Wait: A transaction holds at least one lock while simultaneously requesting additional locks held by other transactions.
  3. No Preemption: Locks cannot be forcibly confiscated from a transaction; locks are released only voluntarily by the holding transaction.
  4. Circular Wait: A closed chain of transactions exists such that $T_0$ waits for a lock held by $T_1$, $T_1$ waits for $T_2$, ..., and $T_n$ waits for $T_0$.

Q58. How does Deadlock Detection work using a Wait-For Graph (WFG)?

Deadlock Detection allows transactions to acquire locks without restriction and periodically inspects the system state to identify circular wait conditions using a Wait-For Graph (WFG).

  1. Graph Construction:
    • Nodes ($V$): Represent active transactions in the database ($T_1, T_2, \dots, T_k$).
    • Directed Edges ($E$): A directed edge $T_i → T_j$ is created if transaction $T_i$ is waiting to lock a resource currently held by transaction $T_j$.
    • When $T_j$ releases the lock and $T_i$ acquires it, the directed edge $T_i → T_j$ is removed.
  2. Deadlock Condition: A deadlock exists in the system if and only if the Wait-For Graph contains a directed cycle.
  3. Recovery: Once a cycle is detected, the DBMS selects a victim transaction (based on minimum cost, age, or fewest locks held) and rolls it back to break the cycle.

Q59. Explain Deadlock Prevention schemes: Wait-Die and Wound-Wait schemes based on timestamps.

Starvation Prevention: When a transaction dies or is wounded, it restarts with its original timestamp, guaranteeing it eventually becomes the oldest transaction and completes without starvation.

Q60. What is Two-Phase Commit Protocol (2PC) in distributed database transactions?

The Two-Phase Commit (2PC) protocol is an atomic commitment protocol that ensures all distributed database nodes (cohorts) either commit or abort a distributed transaction uniformly:

  1. Phase 1: Prepare Phase:
    • The Coordinator node appends a <PREPARE> record to its log and sends a PREPARE message to all participating cohort nodes.
    • Each Cohort checks if it can commit its local operations, flushes undo/redo log records, and replies with either VOTE_COMMIT or VOTE_ABORT.
  2. Phase 2: Commit Phase:
    • Global Commit: If all cohorts voted VOTE_COMMIT, the coordinator writes <GLOBAL_COMMIT> to its log and broadcasts a GLOBAL_COMMIT message to all cohorts. Cohorts commit locally and send an ACK.
    • Global Abort: If any cohort voted VOTE_ABORT or timed out, the coordinator writes <GLOBAL_ABORT> and commands all cohorts to roll back.

Unit V: Concurrency Control, Deadlocks & Storage Recovery

Q61. Explain the 4 classic Concurrency Anomalies: Dirty Read, Non-Repeatable Read, Lost Update, Phantom Read.

When concurrent transactions execute without proper isolation, four classic concurrency anomalies can corrupt database state:

  1. Dirty Read (Temporary Update Anomaly): Occurs when transaction $T_1$ reads a data item modified by transaction $T_2$ that has not yet committed. If $T_2$ subsequently rolls back, $T_1$ has computed results based on an invalid, non-existent database state.
  2. Non-Repeatable Read (Inconsistent Analysis): Occurs when transaction $T_1$ reads a record $X$, and transaction $T_2$ modifies or deletes $X$ and commits. When $T_1$ re-reads $X$, it finds a different value or finds that the record has disappeared.
  3. Lost Update Anomaly: Occurs when two transactions $T_1$ and $T_2$ read the same data item $X$ simultaneously and update it concurrently. The second write completely overwrites the first write without incorporating its modification.
  4. Phantom Read: Occurs when transaction $T_1$ executes a range query (e.g., WHERE Salary > 50000). Concurrently, $T_2$ inserts a new tuple satisfying the condition and commits. When $T_1$ re-executes the query, a new "phantom" row appears.

Q62. What is Two-Phase Locking (2PL) Protocol? Explain Growing Phase and Shrinking Phase.

The Two-Phase Locking (2PL) protocol is a concurrency control mechanism that guarantees conflict serializability by governing when locks can be acquired and released:

  1. Phase 1: Growing (Expanding) Phase:
    • A transaction may acquire new locks (Shared or Exclusive) as needed.
    • Strict Constraint: The transaction is not allowed to release any lock during this phase.
  2. Lock Point: The instantaneous point in time when the transaction has acquired the final lock needed for its execution (marks the end of the growing phase).
  3. Phase 2: Shrinking (Contracting) Phase:
    • A transaction may release locks that are no longer needed.
    • Strict Constraint: The transaction is not allowed to acquire any new lock once it has released even a single lock.

Theorem: Any schedule generated by 2PL is guaranteed to be conflict serializable. However, basic 2PL does not prevent deadlocks or cascading aborts.

Q64. What is Conservative (Static) 2PL and how does it prevent deadlocks?

Conservative 2PL (or Static 2PL) is a deadlock-free variant of the Two-Phase Locking protocol:

  1. Pre-declaration of Locks: Before beginning execution, a transaction must declare all data items it will read or write and attempt to acquire all required locks simultaneously.
  2. All-or-Nothing Locking:
    • If all requested locks are available, the transaction locks them all and proceeds with execution.
    • If even a single lock cannot be acquired immediately, the transaction waits without holding any locks (all temporary locks are released).
  3. Deadlock Freedom: Because transactions never hold resources while waiting for other resources (eliminates the "Hold and Wait" condition), deadlocks are mathematically impossible.
  4. Limitation: In practice, predicting all data items a transaction will access prior to execution is difficult or impossible for interactive queries.

Q65. What are Shared (S) and Exclusive (X) Locks? Draw the Lock Compatibility Matrix.

  2. Exclusive Lock (X-Lock / Write Lock): Requested by a transaction wishing to read and write/modify a data item. Only one transaction can hold an exclusive lock on an item at any instant; all other requests are blocked.

Q66. Explain Lock Conversions (Lock Upgrading and Lock Downgrading) in 2PL.

Lock Conversion provides flexibility by permitting a transaction to transition a lock from one mode to another during its lifecycle:

  1. Lock Upgrade ($S → X$): Converting a Shared (Read) lock to an Exclusive (Write) lock.
    • Permitted only during the Growing Phase of 2PL.
    • Allowed only when no other transaction holds a shared lock on the same item.
    • Use Case: A transaction reads a customer balance, calculates interest, and then upgrades to write the new balance.
  2. Lock Downgrade ($X → S$): Converting an Exclusive (Write) lock to a Shared (Read) lock.
    • Permitted only during the Shrinking Phase of 2PL.
    • Releases exclusive write privilege while allowing the transaction to continue reading without violating serializability.

Q67. Explain the Timestamp Ordering (TO) Protocol for concurrency control.

The Timestamp Ordering (TO) Protocol ensures serializability without locks by assigning every transaction a unique monotonic timestamp $TS(T_i)$ at initiation. Operations are ordered based on transaction timestamps.

Each data item $X$ maintains two timestamps: $R\text{-timestamp}(X)$ (largest timestamp of any transaction that read $X$) and $W\text{-timestamp}(X)$ (largest timestamp of any transaction that wrote $X$).

  1. Read Rule for $T_i$ executing $R(X)$:
    • If $TS(T_i) < W\text{-timestamp}(X)$, $T_i$ needs to read an overwritten value. $T_i$ is rejected and rolled back.
    • If $TS(T_i) \ge W\text{-timestamp}(X)$, operation proceeds: $R\text{-timestamp}(X) = \max(R\text{-timestamp}(X), TS(T_i))$.
  2. Write Rule for $T_i$ executing $W(X)$:
    • If $TS(T_i) < R\text{-timestamp}(X)$, the value produced by $T_i$ was needed previously. $T_i$ is rejected and rolled back.
    • If $TS(T_i) < W\text{-timestamp}(X)$, $T_i$ is attempting to write an obsolete value. $T_i$ is rejected and rolled back.
    • Otherwise, operation proceeds: $W\text{-timestamp}(X) = TS(T_i)$.

Q68. What is Thomas' Write Rule and how does it relax strict timestamp ordering?

Thomas' Write Rule is an optimization of the standard Timestamp Ordering protocol that eliminates unnecessary rollbacks for obsolete write operations:

  1. Condition: When transaction $T_i$ executes $W(X)$ and finds:
    TS(Tᵢ) < W-timestamp(X) (i.e., a younger transaction has already overwritten $X$).
  2. Standard TO Action: Roll back and abort transaction $T_i$.
  3. Thomas' Rule Action: Instead of aborting $T_i$, ignore the write operation and permit $T_i$ to continue execution.
  4. Mathematical Rationale: Because a younger transaction's write has already occurred and is the latest value on disk, ignoring $T_i$'s obsolete write produces an outcome equivalent to executing $T_i$'s write and then immediately overwriting it.
    Significance: Allows schedules that are view serializable but not conflict serializable.

Q69. Explain Validation-Based (Optimistic) Concurrency Control (OCC) and its three phases.

Optimistic Concurrency Control (OCC) assumes that data conflicts between concurrent transactions are rare. It avoids locking during execution and validates transactions prior to commit:

  1. 1. Read Phase:
    • The transaction reads data values from the database and writes all updates to local private workspace variables (copy buffers). No updates touch the database disk.
  2. 2. Validation Phase:
    • The DBMS checks whether the transaction's updates conflict with any concurrently committed transactions.
    • If validation passes (no write-read or write-write collisions), the transaction proceeds to commit.
    • If validation fails, the private copy is discarded and the transaction is aborted and restarted.
  3. 3. Write Phase:
    • If validation was successful, the local updates are copied permanently to the database on disk.

Q70. What is Multiple Granularity Locking (MGL) and explain Intent Locks (IS, IX, SIX)?

Multiple Granularity Locking (MGL) organizes lockable database elements as a tree hierarchy: Database → Area → File → Page → Record. It avoids inspecting thousands of fine-grained locks when locking a coarse-grained container.

Intent Lock Types:

  1. Intent Shared (IS): Indicates an intention to acquire Shared locks at a lower level of the hierarchy.
  2. Intent Exclusive (IX): Indicates an intention to acquire Exclusive locks at a lower level of the hierarchy.
  3. Shared Intent Exclusive (SIX): The current subtree is locked in Shared mode, with the intention of acquiring Exclusive locks on specific descendants.

Locking Rules: To lock a node, all its ancestors in the hierarchy must already be locked with appropriate Intent locks (IS/IX) from top-to-bottom. Locks are released from bottom-to-top.

Q71. What is Multi-Version Concurrency Control (MVCC) and how does it allow readers not to block writers?

Multi-Version Concurrency Control (MVCC) maintains multiple physical versions of each data item (X₁, X₂, …, Xₖ) to ensure that read operations never wait for write locks, and write operations never wait for read locks.

  1. Snapshot Isolation: When a write operation modifies a tuple, the DBMS creates a new version timestamped with the transaction's commit time instead of overwriting the in-place record.
  2. Consistent Reads: When a read operation queries data, it reads the latest committed version that was active as of the reading transaction's snapshot start time.
  3. Garbage Collection (Vacuum): Outdated versions not visible to any active transaction snapshot are periodically purged (e.g., PostgreSQL VACUUM, MySQL Undo Purge).

Q72. Explain Buffer Pool Management policies in recovery: STEAL vs NO-STEAL and FORCE vs NO-FORCE.

The interaction between the DBMS buffer manager and crash recovery is characterized by four orthogonal policies:

PolicyDefinitionRecovery Implication
STEALBuffer manager can flush dirty pages of an uncommitted transaction to disk to free RAM space.Requires UNDO logging: Before-images must be logged to roll back stolen pages on crash.
NO-STEALDirty pages cannot be written to disk until the transaction commits.Zero UNDO overhead; consumes high RAM buffer space.
FORCEAll dirty pages of a transaction must be flushed to disk before commit completes.Zero REDO overhead on crash; causes severe disk I/O write bottleneck.
NO-FORCETransaction can commit once its log records are flushed; data pages can remain in RAM.Requires REDO logging: After-images must be replayed on crash. Provides maximum runtime throughput.

Industry Standard: Modern engines (PostgreSQL, InnoDB, Oracle) use STEAL / NO-FORCE for maximum performance paired with WAL.

Q73. What is the ARIES Recovery Algorithm? Explain Analysis, Redo, and Undo passes.

ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) is the industry-standard crash recovery algorithm based on Write-Ahead Logging (WAL) and repeating history:

  1. 1. Analysis Pass:
    • Scans the log forward from the most recent checkpoint.
    • Reconstructs the state of the Transaction Table (identifies active "loser" transactions at crash time) and the Dirty Page Table (DPT) (identifies pages modified in RAM but not flushed).
  2. 2. Redo Pass ("Repeating History"):
    • Scans forward from the smallest RecLSN in the Dirty Page Table to the end of the log.
    • Replays all logged changes (for both committed and aborted transactions) to restore the exact database state at crash time.
  3. 3. Undo Pass:
    • Scans backward from the end of the log, rolling back changes made by active loser transactions that never committed prior to the crash.
    • Writes Compensation Log Records (CLRs) for each undone action so undo operations are never repeated if another crash occurs.

Q74. What is Shadow Paging recovery technique? Explain its advantages and disadvantages.

Shadow Paging is an alternative recovery technique that maintains two page tables during transaction execution:

  1. Architecture:
    • Current Page Table: Points to the active database pages on disk being modified by the transaction.
    • Shadow Page Table: Kept in read-only state pointing to the original, unmodified pages on disk.
  2. Commit & Abort:
    • Commit: The pointer to the shadow page table is atomicaly replaced with the current page table pointer.
    • Abort: Discard the current page table and reinstate the shadow page table pointer.
  3. Trade-offs:
    Advantages: Zero log generation overhead; instantaneous recovery without Redo or Undo passes.
    Disadvantages: Causes severe disk fragmentation; high page table overhead; difficult to support concurrent transactions.

Q75. How does a Lock Manager implement lock tables, hash tables, and transaction wait queues?

A DBMS Lock Manager is an internal subsystem that coordinates concurrent resource access using high-performance in-memory data structures:

  1. Lock Hash Table: A hash table indexed by data item ID (hash of TableID + PageID + TupleID). Each bucket points to a Lock Head for that resource.
  2. Lock Head Record: Contains:
    • Current Lock Mode: (Shared, Exclusive, or None).
    • Granted List: Linked list of granted lock requests containing transaction ID and mode.
    • Wait Queue: FIFO queue of blocked transaction requests waiting for lock availability.
  3. Lock Request Protocol: When $T_1$ requests an X lock on $X$, the lock manager hashes $X$. If the Granted List is empty, the lock is granted. If incompatible locks exist, $T_1$ is enqueued into the Wait Queue and put to sleep via an OS semaphore or condition variable until signaled.
