1.1 Overview & DBMS Fundamentals

A Database is an organized, logically coherent collection of related data representing some aspect of the real world (often termed the mini-world or Universe of Discourse (UoD)). A database is designed, built, and populated with data for a specific enterprise purpose.

A Database Management System (DBMS) is a complex software system that facilitates the processes of defining, constructing, manipulating, and sharing databases among various users and application programs:

  • Defining: Specifying data types, structures, and business constraints for data to be stored (Metadata definition in Data Dictionary).
  • Constructing: The process of storing data on persistent secondary storage media managed by the DBMS buffer engine.
  • Manipulating: Querying the database to retrieve specific datasets, updating records to reflect state transitions, and generating operational reports.
  • Sharing: Enabling multiple concurrent transactions to access and mutate data concurrently while guaranteeing serializability and isolation.

Technical Note

A database possesses an inherent structure defined by its schema. Unlike arbitrary text documents, every data value in an RDBMS is governed by a strict data type, domain restriction, and integrity rule.

1.2 Database System vs Traditional File Processing System

Prior to DBMS, organizations stored business records in conventional flat files (e.g., CSV, text files, custom binary files) managed directly by the Operating System file system. Application programs written in languages like C, COBOL, or Java manipulated these files directly, introducing severe structural limitations.

Dimension File Processing System Database Management System (DBMS)
1. Data Redundancy & Inconsistency Different application programs create and maintain duplicate files. The same information is stored in multiple formats, causing divergence when updates are made partially. Centralized control eliminates uncontrolled redundancy. Data is stored in normalized relations, providing a single source of truth across all enterprise applications.
2. Ad-Hoc Data Access Answering a new, unanticipated query requires writing, compiling, and testing a brand-new application program from scratch. High-level declarative SQL allows technical and non-technical users to write ad-hoc analytical queries interactively in seconds.
3. Data Isolation & Formats Data is scattered across heterogeneous files with disparate binary and text layouts, making joins across systems arduous. All relations are modeled under a unified conceptual schema. The DBMS engine handles record traversal and cross-table joins automatically.
4. Integrity Constraints Constraints are hardcoded manually inside application code. Adding a business constraint requires patching dozens of programs. Integrity constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY) are declared directly in DDL and validated automatically.
5. Atomicity & Failures System crashes during file writes leave records corrupt, half-written, or in an inconsistent intermediate state with missing funds. The Write-Ahead Logging (WAL) and ACID subsystem guarantee All-or-Nothing atomicity with automated undo/redo recovery.
6. Concurrent Access Anomalies Concurrent writes produce race conditions, dirty reads, and lost updates. Operating system file locks are too coarse-grained. Fine-grained concurrency protocols (Strict 2PL, MVCC, row-level locking) ensure serializable transaction execution.
7. Granular Security OS security permissions are coarse-grained (granting read/write access to the entire file), unable to hide specific columns or rows. Granular Role-Based Access Control (RBAC) allows column-level, row-level, and view-level authorization via GRANT/REVOKE.

1.3 ANSI/SPARC Three-Schema Architecture

The ANSI/SPARC Three-Schema Architecture was proposed in 1975 to establish a clean separation between physical storage implementations and end-user applications. Its primary goal is to achieve Data Independence.

Figure 1.1: ANSI/SPARC 3-Schema Abstraction Architecture and Mappings

The Three Levels of Abstraction:

  1. External Level (View Level / Subschemas): The highest level of abstraction. Describes the customized portion of the database that a specific user group requires, hiding the remaining data for security and simplicity. Multiple external views can coexist over a single conceptual schema.
  2. Conceptual Level (Logical Level / Community Schema): Describes what data is stored in the database and the relationships among those data. It specifies all entity sets, attributes, data types, constraints, and business logic. Managed by the Database Administrator (DBA). Physical storage mechanisms are hidden.
  3. Internal Level (Physical Level / Storage Schema): The lowest level of abstraction. Describes how data is physically laid out on secondary storage (block sizes, byte offsets, indexing trees, hash buckets, record clustering, compression).

1.4 Schemas, Instances and Database States

Formal Distinction: Intension vs Extension

Database Schema (Intension): The overall logical blueprint and structure of the database, specified during the initial design phase. It includes relation names, attribute definitions, and constraints. Changes very infrequently.

Database Instance / State (Extension): The collection of actual data tuples populated in the database at a specific snapshot in time. Every insertion, update, or deletion transitions the database from one valid state to another, while the schema remains invariant.

1.5 Physical & Logical Data Independence

Data Independence is the ability to modify a schema definition at one level of the database system without requiring alterations to the schema definition at the next higher level.

Dimension Formal Mechanism Practical Engineering Example
Logical Data Independence The capacity to modify the conceptual schema without needing to rewrite external schemas or existing application programs. Changes are absorbed by updating the External/Conceptual Mapping. Adding a new attribute (e.g., Passport_No) or decomposing an EMPLOYEE table into EMP_DETAILS and EMP_SALARY without breaking legacy apps querying employee names.
Physical Data Independence The capacity to modify the internal schema without altering the conceptual schema. Changes to storage structures are absorbed by updating the Conceptual/Internal Mapping. Creating a secondary B+ Tree index on Account_Number, altering block sizes, or migrating storage from HDD to NVMe SSD without touching SQL queries or schemas.

1.6 Database Languages & User Interfaces

1. Functional Classification of DBMS Languages

  • Data Definition Language (DDL): Used by designers and DBAs to specify schemas. The DDL compiler parses statements and records table metadata inside the Data Dictionary / System Catalog (CREATE, ALTER, DROP, TRUNCATE).
  • Data Manipulation Language (DML): Used to query, insert, update, and delete stored tuples:
    • Declarative / Non-Procedural DML (SQL): The user states what data is needed without prescribing navigation algorithms. The optimizer chooses the plan.
    • Procedural DML (Relational Algebra): The user instructs the system to perform a specific sequence of procedural operations to compute results.
  • Data Control Language (DCL): Manages security authorization and permission grants (GRANT, REVOKE).
  • Transaction Control Language (TCL): Regulates transactional commit boundaries and rollback saves (COMMIT, ROLLBACK, SAVEPOINT).

1.8 Data Modeling & ER Model Concepts

The Entity-Relationship (ER) Model was proposed by Dr. Peter Chen in 1976. It is a conceptual model that represents the mini-world using entities, attributes, and relationships:

  • Entity: A "thing" or "object" in the real world with an independent existence distinguishable from other objects (e.g., student "Alice", car with VIN 1HGCR2...).
  • Entity Set: A collection of all entities that share the same attributes (e.g., STUDENT, COURSE).
  • Relationship: An association among two or more entities (e.g., Student Alice Enrolls_In Course DBMS).
  • Relationship Set: A mathematical relation over entity sets: R ⊆ {(e1, e2, ... en) | e1 ∈ E1, ... en ∈ En}.

1.9 Complete Attribute Taxonomy

Attributes describe entity sets. In relational modeling, attributes are categorized across three fundamental axes:

Attribute Type Definition & Characteristics Practical Example
Simple (Atomic) Cannot be divided into smaller subcomponents; stores an atomic value from domain. Age, Salary, Gender
Composite Can be decomposed into sub-attributes with independent semantic meanings. Address → {Street, City, Zip}, Name → {First, Last}
Single-Valued Contains exactly one value for each entity instance. Date_Of_Birth, Aadhaar_No
Multi-Valued Can hold a set of multiple values for a single entity instance (double oval in Chen). Phone_Numbers = {9876543210, 9123456780}
Derived Dynamically calculated from stored attributes or clock state (dashed oval in Chen). Age = CURRENT_DATE - DOB
Key Attribute Values are distinct across all entities in the set (solid underline). Roll_No in STUDENT

1.10 ER Diagram Notations (Chen vs Crow's Foot)

Chen's notation uses geometric shapes for conceptual design, while Crow's Foot is standard in relational database modeling tools:

  • Rectangle: Strong Entity Set.
  • Double Rectangle: Weak Entity Set.
  • Diamond: Relationship Set.
  • Double Diamond: Identifying Relationship for a Weak Entity.
  • Oval: Attribute. Double Oval: Multi-valued attribute. Dashed Oval: Derived attribute.
  • Underlined Text in Oval: Primary Key. Dashed underline: Partial Key (Discriminator).

1.11 Mapping Constraints & Cardinality

1. Cardinality Ratios for Binary Relationships

graph LR subgraph OneToOne ["1:1 Relationship (One-to-One)"] D1["Department"] ---|1| M1{Manages} ---|1| F1["Faculty_Head"] end subgraph OneToMany ["1:N Relationship (One-to-Many)"] D2["Department"] ---|1| E2{Employs} ---|N| P2["Professor"] end subgraph ManyToMany ["M:N Relationship (Many-to-Many)"] S3["Student"] ---|M| En3{Enrolls_In} ---|N| C3["Course"] end
  • One-to-One (1:1): An entity in A associates with at most one entity in B, and vice versa (e.g., DEPARTMENT — Manages — FACULTY_HEAD). Foreign Key can be placed on either side (prefer the side with total participation).
  • One-to-Many (1:N): An entity in A associates with any number of entities in B, but B associates with at most one in A (e.g., DEPARTMENT — Employs — PROFESSOR). Foreign Key is placed in the N-side table (Professor).
  • Many-to-One (N:1): Multiple entities in A associate with a single entity in B (e.g., STUDENT — Belongs_To — DEPARTMENT).
  • Many-to-Many (M:N): Entities in A and B can associate with any number of each other (e.g., STUDENT — Enrolls_In — COURSE). Requires a separate Junction / Associative Table with composite primary key.

2. Participation Constraints

  • Total Participation (Double Line): Every entity in the set must participate in the relationship (Existence Dependency).
  • Partial Participation (Single Line): Only some entities participate.

1.13 Database Keys Hierarchy & Mathematical Definitions

Mathematical Set Inclusion

Primary Key ⊆ Candidate Keys ⊆ Super Keys

  • Super Key (SK): A set of attributes that uniquely identifies tuples in a relation. Any superset of a superkey is also a superkey.
  • Candidate Key (CK): A minimal superkey from which no attribute can be removed without losing uniqueness.
  • Primary Key (PK): The designated candidate key chosen by the database designer. Cannot contain NULL (Entity Integrity).
  • Foreign Key (FK): An attribute in child relation referencing the primary key of a parent relation (Referential Integrity).

1.15 EER Aggregation

Aggregation is an abstraction where a relationship set is treated as a higher-level entity set. This allows relationships to participate in other relationships without creating ambiguous ternary structures.

graph LR subgraph Aggregated_Entity ["Aggregated Entity Container: Works_On"] E["Employee"] --- W{Works_On} --- P["Project"] end Aggregated_Entity --- U{Requires} --- M["Machinery"]

Example: (EMPLOYEE — Works_On — PROJECT) is aggregated into a single entity which then associates with MACHINERY via the Requires relationship.

1.16 Higher Degree Relationships (Ternary vs Binary)

A relationship involving n ≥ 3 entity sets simultaneously is an n-ary relationship. Decomposing a ternary relationship SUPPLIES(Supplier, Part, Project) into 3 binary relationships leads to spurious information loss, because binary links cannot capture the atomic ternary constraint that Supplier S supplies Part P specifically for Project J.

1.17 Algorithmic Reduction of ER Diagrams to Relational Tables

7-Step Relational Reduction Protocol

  1. Strong Entity Set: Create a table with all simple attributes. Flatten composite attributes. PK becomes table PK.
  2. Weak Entity Set: Table with all simple attributes + Foreign Key of owner entity. PK = (Owner_PK + Partial_Key).
  3. 1:1 Binary Relationship: Embed PK of one relation into the other as FK (prefer side with total participation).
  4. 1:N Binary Relationship: Embed PK of 1-side into the N-side table as FK + relationship attributes.
  5. M:N Binary Relationship: Create a new associative table. PK = (PK_A + PK_B) as foreign keys.
  6. Multi-Valued Attribute: Create a separate table (Parent_PK, Attribute_Value) where both form composite PK.
  7. Specialization / Generalization: Create separate tables for superclass and subclasses linking via PK/FK.

Worked Example 3: Combinatorial Calculation of Superkeys

Step-by-Step Calculation: Principle of Inclusion-Exclusion

Problem: Given relation schema $R(A, B, C, D, E, F)$ with Candidate Keys $K_1 = \{A, B\}$ and $K_2 = \{C\}$. Calculate the total count of valid superkeys for relation $R$.

Analytical Solution:

  1. Total attributes $n = 6$.
  2. Any superkey derived from $K_1 = \{A, B\}$ must contain both $A$ and $B$. The remaining $n - |K_1| = 6 - 2 = 4$ attributes can each be either included or excluded ($2^4 = 16$ combinations): $$\text{Count}(SK_{AB}) = 2^4 = 16$$
  3. Any superkey derived from $K_2 = \{C\}$ must contain $C$. The remaining $n - |K_2| = 6 - 1 = 5$ attributes give: $$\text{Count}(SK_C) = 2^5 = 32$$
  4. Superkeys containing both $\{A, B\}$ and $\{C\}$ contain $\{A, B, C\}$. The remaining $6 - 3 = 3$ attributes give: $$\text{Count}(SK_{AB} \cap SK_C) = 2^3 = 8$$
  5. By the Principle of Inclusion-Exclusion: $$\text{Total Superkeys} = |SK_{AB}| + |SK_C| - |SK_{AB} \cap SK_C| = 16 + 32 - 8 = \mathbf{40}$$
