What is Data Independency in DBMS?

Data Independence is the capacity to modify the schema definition at one level of the three-schema database architecture without requiring modifications to the schema definition at the next higher level. It insulates applications and queries from changes in data organization and storage.

  1. Logical Data Independence: The ability to alter the conceptual schema (e.g., adding/deleting attributes, splitting relations, or creating new entity tables) without modifying external schemas (user views) or existing application programs.
    Example: Splitting an Employee table into Emp_Personal and Emp_Salary can be masked by creating a view joining both tables.
  2. Physical Data Independence: The ability to alter the internal/physical storage schema (e.g., creating B+ tree indexes, reorganizing file records, migrating to SSDs) without altering conceptual schemas or application code.
    Example: Adding an index on Student(Roll_No) speeds up search queries from O(N) to O(1) without requiring any changes to user SQL queries.

Exam Note: Logical data independence is significantly harder to achieve because applications are tightly coupled to conceptual attributes.

What are different Integrity Constraints?

Integrity Constraints are declarative assertions enforced by the DBMS engine to guarantee that database modifications do not result in semantic inconsistency or data corruption:

  1. Domain Constraint: Restricts attribute values to valid atomic data types, ranges, or enumerated sets.
    Example: CHECK(Age >= 18) or Gender IN ('M', 'F', 'Other').
  2. Key Constraint (Uniqueness): Mandates that candidate key attributes must uniquely identify every tuple in a relation:
    ∀ t₁, t₂ ∈ r(R), t₁ ≠ t₂ ⇒ t₁[CK] ≠ t₂[CK].
  3. Entity Integrity Constraint: Mandates that no attribute participating in the Primary Key of a base relation can contain a NULL value:
    ∀ t ∈ r(R), t[PK] ≠ NULL.
  4. Referential Integrity Constraint: Enforces valid foreign key references between child and parent tables:
    FK ∈ r₁(R₁) ⊆ πPK(r₂(R₂)). If referenced row is deleted, actions like CASCADE or SET NULL are triggered.

Explain different Features of SQL.

SQL (Structured Query Language) is a standardized, declarative, non-procedural language for managing relational database systems. Key features include:

  1. Comprehensive Command Scope: Integrates DDL (schema design), DML (data access), DQL (querying), DCL (permissions), and TCL (transactions) under a unified syntax.
  2. Declarative & Set-Oriented: Users specify what data to retrieve rather than how to retrieve it, operating on entire sets of records simultaneously rather than single records.
  3. Rich Querying Capabilities: Built-in support for Cartesian products, inner/outer joins, nested subqueries, set operations (UNION, INTERSECT), and grouping/aggregation (GROUP BY, HAVING).
  4. Integrity & Security Enforcement: Declarative definition of primary keys, foreign keys, check constraints, user roles, and fine-grained access control via GRANT / REVOKE.
  5. ACID Transaction Control: Provides explicit boundaries for transaction atomicity and durability via COMMIT, ROLLBACK, and SAVEPOINT.
2 MARKS UNIT 3 Q5
What are advantages of normalization?

Database Normalization is the systematic process of decomposing complex relations with redundancy into smaller, well-structured relations. Key benefits include:

  1. Elimination of Data Anomalies:
    • Insertion Anomaly: Cannot record an independent fact without artificially adding unrelated entity data.
    • Deletion Anomaly: Unintended loss of crucial business information when deleting an unrelated tuple.
    • Update Anomaly: Inconsistent data states resulting from partial updates across redundant rows.
  2. Minimization of Storage Redundancy: Reduces repetitive attribute values across tuples, optimizing disk space and RAM cache utilization.
  3. Lossless Join Guarantee: Decomposed sub-relations can be perfectly recombined via natural join without creating spurious tuples.
  4. Dependency Preservation: Ensures business rules and functional dependencies can be validated on individual tables without cross-table joins.
2 MARKS UNIT 3 Q6
Write different Inference Rule for Functional Dependency?

Armstrong's Axioms form a complete and sound set of inference rules used to compute the closure of functional dependencies (F⁺):

  1. Primary Axioms:
    • Reflexivity: If Y ⊆ X, then X → Y holds (Trivial dependency).
    • Augmentation: If X → Y, then XZ → YZ for any attribute set Z.
    • Transitivity: If X → Y and Y → Z, then X → Z.
  2. Secondary (Derived) Rules:
    • Union Rule: If X → Y and X → Z, then X → YZ.
    • Decomposition Rule: If X → YZ, then X → Y and X → Z.
    • Pseudo-transitivity Rule: If X → Y and γY → Z, then γX → Z.
2 MARKS UNIT 4 Q7
What are ACID properties of Transaction?

Every database transaction must strictly satisfy the ACID Properties to maintain database correctness during concurrent access and system failures:

  1. Atomicity ("All-or-Nothing"): Guarantees that either all operations of a transaction execute successfully or none do. Handled by the Recovery Manager via undo logging.
    Banking Example: Deducting ₹100 from Account A and crediting ₹100 to Account B must both succeed; if crash occurs between them, the deduction is undone.
  2. Consistency: Execution of a transaction in isolation preserves all database invariants, integrity constraints, and domain checks (BalanceA + BalanceB = Constant).
  3. Isolation: Concurrent transactions execute without mutual interference; intermediate states are invisible to concurrent transactions. Enforced by the Concurrency Control Manager.
  4. Durability: Once a transaction commits, its modifications persist permanently in non-volatile storage, surviving subsequent power outages or crashes. Enforced via Write-Ahead Logging (WAL).
2 MARKS UNIT 4 Q8
What are various reasons for transaction failure?

Transactions in a DBMS can fail due to three broad categories of operational faults:

  1. Logical / Internal Errors: Errors originating within the application or query logic, such as:
    • Division by zero or arithmetic overflow.
    • Violations of declared schema integrity constraints (e.g., duplicate primary key, foreign key mismatch).
    • Bad user input or data not found exceptions.
  2. System / Concurrency Errors: Faults detected and triggered by the DBMS transaction manager:
    • Deadlock Abort: The transaction is chosen as a victim in a Wait-For Graph cycle and rolled back.
    • Serializability Violations: Invalidation in optimistic concurrency control or timestamp ordering conflicts.
    • Resource exhaustion (e.g., out of lock table memory or buffer pool exhaustion).
  3. System Crashes & Hardware Failures: Sudden termination of server hardware or OS:
    • Power failure, operating system panic, or CPU fault causing RAM loss.
    • Disk head crash or unrecoverable sector corruption (media failure).
2 MARKS UNIT 4 Q9
What are Concurrent Transactions?

Concurrent Transactions are multiple transactions whose execution lifetimes overlap in time within the database system.

  1. Execution Mechanism: In single-processor environments, operations (reads/writes) of concurrent transactions are interleaved chronologically. In multi-core/distributed environments, operations execute in parallel across separate processors.
  2. Primary Benefits:
    • Increased Throughput: Allows CPU to process another transaction's computation while the current transaction waits for disk I/O.
    • Reduced Turnaround Time: Prevents short transactions from waiting behind lengthy batch jobs (eliminates head-of-line blocking).
  3. Critical Requirement: Uncontrolled concurrency leads to anomalies (Dirty Read, Lost Update, Phantom Read). The DBMS must enforce serializability using concurrency control protocols (2PL, Timestamping).
2 MARKS UNIT 5 Q10
What is Lock in Transaction Management?

A Lock is a concurrency control synchronization variable associated with a data item (database, table, page, or tuple) that regulates concurrent access permissions to prevent data inconsistencies.

  1. Shared Lock (S-Lock / Read Lock): Requested by a transaction wishing to read a data item. Multiple transactions can hold shared locks concurrently on the same item (S + S = Allowed).
  2. Exclusive Lock (X-Lock / Write Lock): Requested by a transaction wishing to modify or write to a data item. Only one transaction can hold an exclusive lock on an item; all other concurrent read and write requests are blocked (X + S = Blocked, X + X = Blocked).
  3. Lock Management: Maintained by the DBMS Lock Manager using in-memory hash tables and wait queues to prevent race conditions.
2 MARKS UNIT 1 Q11
Define the evolution of database.

Database management architectures have evolved over several distinct historical generations:

  1. Flat-File Processing (1960s): Application-specific operating system files. Suffered from severe data redundancy, inconsistency, tight program-data coupling, and zero concurrent write isolation.
  2. Hierarchical Data Model (Late 1960s, IBM IMS): Tree-structured hierarchy where records are organized as parent-child nodes (1:N relationships) navigated through rigid physical disk pointers.
  3. Network Data Model (1970s, CODASYL DBTG): Graph-based network where child records can possess multiple parent records (M:N relationships), traversed via complex pointer arrays.
  4. Relational Model (1970, Dr. E.F. Codd, IBM System R): Two-dimensional relations (tables) with rows (tuples) and columns (attributes), manipulated declaratively using relational algebra and standardized SQL without exposing physical access paths.
  5. Object-Oriented & Object-Relational (1990s): Supported encapsulation, complex inheritance, multimedia data types, and stored user-defined methods alongside relational tables.
  6. NoSQL & NewSQL (2000s–Present): Distributed document stores (MongoDB), key-value stores (Redis), columnar stores (Cassandra), and horizontally scalable ACID relational engines (Google Spanner, CockroachDB).

Define aggregation with example.

Aggregation is an abstraction in Entity-Relationship (ER) modeling that treats a relationship set (and its participating entity sets) as a single higher-level entity set, allowing it to participate in further relationships.

  1. Why It Is Needed: Standard ER diagrams cannot establish a relationship between an entity set and another relationship set directly. Aggregation solves this by enclosing the relationship in a virtual entity container.
  2. Practical Scenario & Example:
    • Suppose employees work on projects: Works_On(Employee, Project).
    • Now, suppose that specific assignment requires specialized machinery: Requires(Works_On, Machinery).
    • Here, Requires cannot connect directly to the diamond Works_On. Instead, the relationship Works_On is aggregated into a rectangular entity box that connects to Requires.

What are different relational algebra operations?

Relational Algebra operations are categorized into fundamental and extended operations:

  1. Fundamental Operations (Complete Set):
    • Selection (σp(R)): Filters tuples satisfying predicate $p$.
    • Projection (πL(R)): Extracts specified attribute columns $L$, eliminating duplicates.
    • Cartesian Product (R × S): Combines every tuple of $R$ with every tuple of $S$.
    • Set Union (R ∪ S): Returns all tuples in $R$ or $S$ (requires union compatibility).
    • Set Difference (R - S): Returns tuples in $R$ that are not in $S$.
    • Rename (ρS(R)): Renames relation schema or attribute names.
  2. Derived / Extended Operations:
    • Set Intersection (R ∩ S = R - (R - S)).
    • Natural Join (R ⋈ S) & Theta Join (R ⋈_θ S).
    • Division (R ÷ S): Used for "for all" queries.
    • Outer Joins: Left (⋈L), Right (⋈R), and Full (⋈F) outer joins.
2 MARKS UNIT 3 Q16
What is Boyce-Codd Normal Form in the DBMS?

A relation schema R is in Boyce-Codd Normal Form (BCNF) if and only if, for every non-trivial functional dependency X → A that holds on R, the determinant attribute set X is a Superkey of R.

Key Properties & Exam Insights:

  1. Strict Superkey Determinant: Unlike 3NF (which permits non-superkey determinants if the dependent attribute is prime), BCNF strictly disallows any non-superkey determinant:
    X → A ⇒ X is a Superkey.
  2. Subsumption Hierarchy: BCNF ⊆ 3NF ⊆ 2NF ⊆ 1NF. Every relation in BCNF is guaranteed to be in 3NF.
  3. Trade-Off: Any relation can be decomposed into BCNF with a Lossless Join guarantee, but BCNF decomposition does not always preserve functional dependencies.
  4. Example: In R(Student, Subject, Teacher) where {Student, Subject} → Teacher and Teacher → Subject, the schema is in 3NF but violates BCNF because Teacher is not a superkey.

2 MARKS UNIT 1 Q21
What do you mean by currency with respect to database?

In database systems, Currency (Data Freshness / Timeliness) refers to how up-to-date and synchronized the currently retrieved data values are relative to real-world state changes and the latest committed transactions.

  1. Currency vs Concurrency: While Concurrency refers to multiple transactions executing simultaneously, Currency measures temporal lag between data modifications and their visibility in read views, materialized caches, or read-replicas.
  2. Currency Indicators:
    • Current (Fresh) Read: Query reads the latest committed transaction state directly from the primary database engine.
    • Stale Read: Query reads from an asynchronously replicated replica or cached snapshot where recent commits have not yet propagated.
  3. Exam Note: In distributed architectures, maintaining strict instantaneous currency across all replica nodes requires synchronous two-phase commit, reducing write throughput (CAP theorem trade-off).
2 MARKS UNIT 2 Q22
What is Relational Calculus?

Relational Calculus is a formal, non-procedural (declarative) query language based on first-order predicate calculus. Rather than detailing an procedural step-by-step algorithm, it describes the mathematical properties of the desired result.

  1. Tuple Relational Calculus (TRC): Queries specify predicate conditions over complete relation tuples:
    { t | P(t) } (e.g., { t | t ∈ Instructor ∧ t[Salary] > 50000 }).
  2. Domain Relational Calculus (DRC): Queries specify predicates over individual attribute domain variables:
    { ⟨ x₁, x₂, …, xₙ ⟩ | P(x₁, x₂, …, xₙ) }.
  3. Codd's Equivalence Theorem: Relational Algebra, safe TRC, and safe DRC are mathematically equivalent in expressive power; any language that expresses these is said to be Relationally Complete.
2 MARKS UNIT 2 Q23
What is Equi-Join in database?

An Equi-Join is a specialized Theta Join operation where the join predicate uses exclusively the equality comparison operator (=) between matching attributes from two relations.

  1. Mathematical Definition:
    R ⋈R.A = S.B S = σR.A = S.B(R × S)
  2. SQL Syntax Example:
    SELECT * FROM Student JOIN Enroll ON Student.Roll_No = Enroll.Roll_No;
  3. Difference from Natural Join:
    • In an Equi-Join, both join attributes (Student.Roll_No and Enroll.Roll_No) are retained in the result schema, appearing as duplicate columns.
    • In a Natural Join (⋈), identically named matching attributes are merged, eliminating the duplicate column from the output.

What is a CLAUSE in terms of SQL?

In SQL, a CLAUSE is a syntactic sub-component of an SQL statement that provides a specific operational directive, filtering predicate, ordering rule, or data definition parameter.

  1. Primary Query Clauses:
    • SELECT clause: Specifies the projection list of columns or computed aggregate expressions.
    • FROM clause: Identifies the participating tables, views, or join expressions.

    • GROUP BY clause: Partitions result rows into summary groups based on common attribute values.
    • HAVING clause: Filters aggregated groups using predicate conditions on aggregate functions.
    • ORDER BY clause: Sorts the output result set in ascending (ASC) or descending (DESC) order.
  2. Logical Processing Order: SQL engines logically evaluate clauses in order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
2 MARKS UNIT 3 Q25
Define the closure of an attribute set.

The Closure of an Attribute Set X (denoted X⁺) under a given set of functional dependencies F is the complete set of all attributes that are functionally determined by X under F.

  1. Algorithm to Compute X⁺:
    • Initialize: X⁺ = X.
    • Repeat until no new attributes are added: If there exists an FD Y → Z ∈ F such that Y ⊂eq X⁺, then update X⁺ = X⁺ ∪ Z.
  2. Concrete Example: Given R(A, B, C, D) and F = {A → B, B → C, C → D}:
    To find A⁺: Initial {A} → using A → B → {A, B} → using B → C → {A, B, C} → using C → D → A⁺ = {A, B, C, D}.
  3. Primary Use: Used to test whether an attribute set is a Superkey (if X⁺ = R) and to verify if an FD X → Y is implied by F (if Y ⊂eq X⁺).
2 MARKS UNIT 4 Q26
When is a transaction Rolled Back?

A transaction is Rolled Back (Aborted) when its execution cannot complete successfully, requiring the DBMS to undo all uncommitted writes and restore the database to its pre-transaction state.

  1. Triggers for Rollback:
    • Explicit Application Abort: Application logic issues a ROLLBACK statement due to business logic rejection (e.g., insufficient bank account balance).
    • Integrity Constraint Violation: An INSERT or UPDATE violates a Primary Key, Foreign Key, or CHECK constraint.
    • Deadlock Resolution: The DBMS deadlock detection manager selects the transaction as a "victim" to break a cycle in the Wait-For Graph.
    • System Crash: A power outage or OS fault occurs before the transaction flushes its <COMMIT> log record (handled during recovery).
  2. Mechanism: Handled by the Recovery Manager using the transaction log, reading backward and restoring before-images (undo pass).
2 MARKS UNIT 5 Q27
List the various levels of locking?

The Levels (Granularity) of Locking define the physical and logical scale of database items that can be locked independently by the concurrency control subsystem:

  1. Database Level: The entire database is locked. Minimum lock overhead; zero concurrency (used for administrative offline backups).
  2. Table / Relation Level: An entire table is locked. Suitable for bulk batch loading operations.
  3. Page / Disk Block Level: A physical disk block (typically 4 KB – 8 KB) containing multiple tuples is locked. Common in legacy engines.
  4. Tuple / Row Level: Individual record tuples are locked. Maximum concurrent transaction throughput; standard in modern RDBMSs (PostgreSQL, MySQL InnoDB, Oracle).
  5. Field / Attribute Level: Individual columns within a row are locked. Maximum theoretical concurrency, but prohibitive lock table memory overhead.

Trade-Off: Coarser granularity minimizes lock maintenance overhead but reduces concurrency; finer granularity maximizes concurrency but incurs high memory and CPU lock overhead.

2 MARKS UNIT 1 Q29
List any four disadvantages of file system approach over database approach.

Four critical disadvantages of the conventional File Processing System approach compared to a modern DBMS:

  1. Uncontrolled Data Redundancy & Inconsistency: Multiple application programs store duplicate copies of the same data files. Updating one file leaves others outdated, causing conflicting inconsistent records.
  2. Tight Program-Data Dependence: Physical record layout and file format are hardcoded into application source code. Any file schema change requires rewriting and recompiling all dependent programs (zero data independence).
  3. Lack of Atomic Crash Recovery: If a computer crashes midway through an update, files are left partially written with corrupted records; no automated rollback or undo logging exists.
  4. Poor Concurrency Isolation & Security: File systems lack row-level locking, leading to lost updates during concurrent edits. Security is limited to basic OS file permissions without granular column/row access control.

List all prime and non-prime attributes In Relation R(A,B,C,D,E) with FD set F = {AB→C, B→E, C→D}.

Given relation schema R(A, B, C, D, E) with functional dependency set:

F = {AB → C, B → E, C → D}
  1. Attribute Closure Analysis:
    • Attribute $A$ does not appear on the RHS of any FD; attribute $B$ also never appears on any RHS. Thus, {A, B} must be part of every candidate key.

      (AB)⁺ = {A, B} ∪ {C} (via AB → C) ∪ {E} (via B → E) ∪ {D} (via C → D) = {A, B, C, D, E} = R.
    • Since (AB)⁺ = R and no proper subset of {AB} generates all attributes, {AB} is the unique Candidate Key.
  2. Classification of Attributes:
    • Prime Attributes (attributes part of any candidate key): \{A, B\}.
    • Non-Prime Attributes (attributes not part of any candidate key): \{C, D, E\}.
2 MARKS UNIT 3 Q32
Explain MVD with the help of suitable example.

A Multi-Valued Dependency (MVD), denoted as X ↠ Y (or X →→ Y), holds on relation schema R if, for any two tuples t₁ and t₂ that agree on attribute set X (i.e. t₁[X] = t₂[X]), there also exist tuples t₃ and t₄ in R such that:

t₃[X] = t₄[X] = t₁[X] = t₂[X],   t₃[Y] = t₁[Y],   t₃[R − (X ∪ Y)] = t₂[R − (X ∪ Y)]
  1. Practical Intuition: An MVD occurs when two independent 1:N relationships are combined into a single table, resulting in an unnatural Cartesian cross-product of attribute values.
  2. Example: Consider Teacher_Info(Teacher, Course, Hobby):
    A teacher can teach multiple independent courses and have multiple independent hobbies. If Prof. John teaches {DBMS, OS} and enjoys hobbies {Cricket, Music}, the table must contain 4 tuples to remain consistent:
    (John, DBMS, Cricket), (John, DBMS, Music), (John, OS, Cricket), (John, OS, Music).
    Here, Teacher ↠ Course and Teacher ↠ Hobby.
  3. Resolution: MVD anomalies are resolved in Fourth Normal Form (4NF) by decomposing the table into two separate tables: Teacher_Courses(Teacher, Course) and Teacher_Hobbies(Teacher, Hobby).
2 MARKS UNIT 4 Q33
Discuss Consistency and Isolation property of a transaction.

Detailed examination of the Consistency and Isolation properties of database transactions:

  1. Consistency:
    • Definition: Guarantees that the execution of a transaction in isolation transforms the database from one valid consistent state to another valid consistent state, preserving all schema constraints and domain invariants.
    • Enforcement: Jointly enforced by the application programmer (correct business logic) and the DBMS (declarative constraints like PRIMARY KEY, FOREIGN KEY, CHECK).
    • Example: In bank account transfers, the total sum of balances across accounts must remain invariant before and after execution (∑ Balancesafter = ∑ Balancesbefore).
  2. Isolation:
    • Definition: Guarantees that concurrent transactions execute without mutual interference. Intermediate uncommitted state modifications of a transaction are completely hidden from other concurrent transactions.
    • Enforcement: Managed exclusively by the DBMS Concurrency Control Manager using locking protocols (2PL), timestamp ordering, or multi-version concurrency control (MVCC).
    • SQL Isolation Levels: Read Uncommitted → Read Committed → Repeatable Read → Serializable.
2 MARKS UNIT 4 Q34
Draw a state diagram and discuss the typical states that a transaction goesthrough during execution.

During its execution lifecycle, a database transaction transitions through several distinct states:

  1. Active: The initial state where the transaction begins executing its read and write statements.
  2. Partially Committed: Entered immediately after the final statement of the transaction has completed execution, but before log records are flushed to disk.
  3. Committed: Reached after all log records and updates are safely flushed to stable non-volatile storage. The transaction has completed successfully.
  4. Failed: Entered when regular execution can no longer proceed due to logical errors, constraint violations, or system aborts.
  5. Aborted: Reached after the rollback operation completes and the database state is restored to its pre-transaction state via the undo log.

Define 3 NF.

A relation schema R is in Third Normal Form (3NF) if and only if it is in Second Normal Form (2NF) and, for every non-trivial functional dependency X → A that holds on R, at least one of the following conditions is satisfied:

2 MARKS UNIT 4 Q54
What do you mean by testing of serializability?

Testing of Serializability is the algorithmic process of determining whether a concurrent schedule produces an outcome equivalent to some serial schedule:

  1. Testing Conflict Serializability (Precedence Graph Method):
    • Construct a directed graph $G = (V, E)$ where nodes $V$ represent transactions.
    • Draw a directed edge $T_i \to T_j$ if an operation of $T_i$ precedes and conflicts with an operation of $T_j$ on the same data item ($R/W$, $W/R$, or $W/W$).
    • Result: The schedule is conflict serializable if and only if the graph contains NO directed cycles. Tested in polynomial time O(V + E) via topological sort.
  2. Testing View Serializability: Verified by checking three view equivalence criteria (initial read, read-from, final write) against all $n!$ possible serial schedules. Testing view serializability is NP-Complete.

Define exclusive lock.

What is Functional Dependency? Explain the procedure of calculating the Canonical Cover of a given Functional Dependency Set with suitable example.

1. Definition of Minimal Cover (Canonical Cover)

A Minimal Cover Fc of a functional dependency set F is an equivalent simplified set of FDs (Fc ≡ F) that satisfies three essential minimality conditions:

  1. Every functional dependency in Fc has a single attribute on its Right-Hand Side (RHS).
  2. No functional dependency in Fc contains an extraneous attribute on its Left-Hand Side (LHS) or RHS.
  3. No functional dependency in Fc is redundant (i.e., removing any FD X → Y from Fc results in a strictly weaker set F' ¬≡ F).

2. Three-Step Synthesis Algorithm

  1. Decomposition of RHS (Canonical Form):

    Apply the Armstrong Decomposition Rule to split multi-attribute RHS dependencies:

    • Transform X → A₁ A₂ … Aₖ into individual dependencies: X → A₁, X → A₂, …, X → Aₖ.
  2. Elimination of Extraneous Attributes:

    Test each remaining dependency for superfluous attributes:

    • Extraneous on LHS: In dependency XA → B, attribute A is extraneous on the LHS if B ∈ X⁺ under F. If so, replace XA → B with X → B.
    • Extraneous on RHS: In dependency X → AB, attribute A is extraneous on the RHS if A ∈ X⁺ under (F - {X → A}).
  3. Elimination of Redundant Dependencies:

    For each individual FD X → Y ∈ Fc:

    • Temporarily construct F' = Fc - {X → Y}.
    • Compute the attribute closure X⁺ under the reduced set F'.
    • If Y ⊂eq X⁺F', the dependency X → Y is redundant and must be removed permanently from Fc.

7 MARKS UNIT 4 Q13
Explain Deadlock Handling with Suitable Example.

1. Deadlock Definition & Coffman Conditions

A Deadlock occurs in concurrent database systems when two or more transactions are in a simultaneous circular wait state, each waiting to acquire a lock on a data resource currently held by another transaction in the cycle.

2. Deadlock Handling Strategies

  1. Deadlock Prevention (Timestamp Schemes):

    Transactions are assigned unique monotonic timestamps TS(Tᵢ) when they begin. Deadlocks are prevented dynamically:

    • Wait-Die Scheme (Non-Preemptive):
      If an older transaction Tᵢ (TS(Tᵢ) < TS(Tⱼ)) requests a lock held by younger Tⱼ, Tᵢ is permitted to wait.
      If a younger transaction requests a lock held by an older transaction, the younger transaction is killed and rolled back (dies).
    • Wound-Wait Scheme (Preemptive):
      If an older transaction requests a lock held by a younger transaction, the older transaction wounds the younger one, forcing it to abort and roll back.
      If a younger transaction requests a lock held by an older transaction, the younger transaction is allowed to wait.
  2. Deadlock Detection & Recovery:

    Locks are granted freely without pre-conditions. The DBMS periodically inspects the system for circular waits:

    • Wait-For Graph (WFG): Constructs directed graph G = (V, E) where edges Tᵢ → Tⱼ indicate Tᵢ is waiting for a lock held by Tⱼ. A deadlock exists if and only if the WFG contains a directed cycle.
    • Victim Selection: Rolls back the transaction with minimum cost (fewest locks held, lowest CPU time consumed).

Explain Time Stamp Based Concurrency Control technique.

1. Timestamp Ordering (TO) Mechanics

Each transaction Tᵢ is assigned a unique monotonically increasing timestamp TS(Tᵢ) upon entering the system. Each data item Q maintains two operational timestamps:

  • W-timestamp(Q): Largest timestamp of any transaction that successfully executed Write(Q).
  • R-timestamp(Q): Largest timestamp of any transaction that successfully executed Read(Q).

2. Operational Execution Rules

  1. Read Operation Protocol (Tᵢ issues Read(Q)):
    • If TS(Tᵢ) < W-timestamp(Q): Transaction Tᵢ is attempting to read an overwritten obsolete value. Abort and restart Tᵢ with a new timestamp.
    • If TS(Tᵢ) ≥ W-timestamp(Q): Execute Read(Q) successfully and update timestamp:
      R-timestamp(Q) = max(R-timestamp(Q), TS(Tᵢ)).
  2. Write Operation Protocol (Tᵢ issues Write(Q)):
    • If TS(Tᵢ) < R-timestamp(Q): The value produced by Tᵢ was needed previously by a younger transaction. Abort and restart Tᵢ.
    • If TS(Tᵢ) < W-timestamp(Q): Transaction Tᵢ is attempting to overwrite a newer value.
      Standard TO: Abort and restart Tᵢ.
      Thomas' Write Rule: Simply ignore the obsolete write and permit Tᵢ to proceed!
    • Otherwise: Execute Write(Q) successfully and set W-timestamp(Q) = TS(Tᵢ).

7 MARKS UNIT 4 Q43
Discuss the procedure of deadlock detection and recovery in transaction.

1. Deadlock Detection Using Wait-For Graph (WFG)

The DBMS maintains an internal dynamic directed graph G = (V, E) where vertices V represent transactions and directed edges Tᵢ → Tⱼ represent Tᵢ waiting for a resource locked by Tⱼ. A deadlock exists if and only if a directed cycle exists in the WFG.

2. Three-Step Deadlock Recovery Procedure

  1. Victim Selection:

    The DBMS selects which transaction in the cycle to abort based on minimal recovery penalty:

    • Transaction with fewest locks acquired.
    • Transaction that has consumed the least CPU execution time.
    • Transaction that has performed the fewest data modifications (least undo work).
  2. Rollback Execution:

    Once a victim transaction is selected, the DBMS decides the extent of rollback:

    • Total Rollback: Abort the victim transaction entirely, undo all its modifications, and restart it from the beginning.
    • Partial Rollback: Roll back the victim only to a recent SAVEPOINT sufficient to release the conflicting lock and break the cycle.
  3. Starvation Prevention:

    Ensure that the exact same transaction is not repeatedly selected as a victim. The DBMS tracks victim counts and incorporates transaction age into victim selection metrics.

What is Log? How is it maintained? Discuss the features of deferred database modification and immediate database modification in brief.

1. Transaction Log & Maintenance

A Log is an append-only, sequential, non-volatile file recording all transaction state transitions and data modifications. Maintained via the Write-Ahead Logging (WAL) protocol (log records must reach disk before modified dirty data pages are flushed).

2. Deferred vs Immediate Database Modification:

Feature Deferred Database Modification Immediate Database Modification
Disk Write Timing Updates deferred until transaction reaches Commit. Updates written to disk dynamically during active execution.
Log Requirements Records only After-Image (NewValue for REDO). Records both Before-Image (OldValue) and After-Image.
Crash Recovery Pass REDO-Only recovery; no UNDO required. Both UNDO and REDO passes required.
7 MARKS UNIT 5 Q82
What are multi version schemes of concurrency control? Describe with the help of an example. Discuss the various Time stamping protocols for concurrency control also.

1. Multi-Version Concurrency Control (MVCC)

In MVCC, each write operation creates a timestamped version of the record ⟨ Qₖ, Data, WTS(Qₖ), RTS(Qₖ) ⟩.

  • Read Operation: Reads the latest version whose write timestamp WTS ≤ TS(Tᵢ). Readers never block writers, and writers never block readers.

2. Timestamping Protocols Summary

  1. Basic Timestamp Ordering (TO): Aborts transactions that attempt out-of-order reads or writes.
  2. Thomas Write Rule: Ignores obsolete blind writes (TS(Tᵢ) < WTS(Q)) without aborting the transaction, achieving view serializability.
  3. Strict Timestamp Ordering: Delays reads and writes on uncommitted versions until the writing transaction commits, ensuring strict recoverable executions.
