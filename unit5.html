5.1 The 4 Classic Concurrency Anomalies

Uncontrolled concurrent execution of transactions without synchronization leads to 4 severe data corruption anomalies:

Anomaly Interleaved Scenario Engine Consequence
1. Dirty Read
(Temporary Update)		 T1 updates item X. T2 reads the uncommitted value of X. T1 encounters an error and aborts. T2 continues calculations on phantom data that was rolled back and never existed.
2. Lost Update
(Blind Overwrite)		 T1 and T2 read X simultaneously. T1 updates and writes X. T2 updates based on old value and overwrites X. T1's update is completely erased by T2's overwrite without synchronization.
3. Non-Repeatable Read
(Fuzzy Read)		 T1 reads X. T2 updates or deletes X and commits. T1 re-reads X within the same transaction. T1 observes two different values for the exact same record during its execution.
4. Phantom Read
(Predicate Shift)		 T1 scans tuples satisfying predicate P. T2 inserts a new row satisfying P and commits. T1 scans again. T1 discovers a new "phantom" row appearing midway through transaction execution.

5.2 Locking & The Two-Phase Locking (2PL) Protocol

A Lock is a concurrency variable that regulates access to data items. The two primary lock modes are:

  • Shared Lock (S-lock): Acquired for reading. Multiple transactions can hold shared locks on the same data item concurrently.
  • Exclusive Lock (X-lock): Acquired for writing. Only ONE transaction can hold an exclusive lock; no other transaction can read or write.

5.3 2PL Protocol Variants & Timelines

The Two-Phase Locking (2PL) protocol guarantees Conflict Serializability by requiring transactions to lock and unlock in two distinct phases:

  1. Growing (Expanding) Phase: The transaction may acquire new locks, but cannot release any locks.
  2. Shrinking (Contracting) Phase: The transaction may release locks, but cannot acquire any new locks. The point where the last lock is acquired is the Lock Point.
2PL Protocol Variant Operational Invariant Guaranteed Properties
Basic 2PL Locks acquired in growing phase, released in shrinking phase. Guarantees Serializability; subject to cascading aborts and deadlocks.
Strict 2PL All Exclusive (X) locks must be held until transaction commits or aborts. Guarantees Serializability + Cascadeless / Strict recovery. Industry standard.
Rigorous 2PL All Shared (S) AND Exclusive (X) locks held until commit/abort. Guarantees Serializability + Strict recovery. Serial order matches commit order.
Conservative 2PL Acquires all needed locks simultaneously before starting execution. Guarantees Deadlock-Free execution; requires prior knowledge of read/write sets.

5.4 Lock Conversions & Lock Manager

  • Lock Upgrade: Converting a Shared Lock (S) into an Exclusive Lock (X). Permissible only during the Growing Phase.
  • Lock Downgrade: Converting an Exclusive Lock (X) into a Shared Lock (S). Permissible only during the Shrinking Phase.
  • Lock Manager: In-memory hash table indexed by data item ID containing granted lock modes and linked queues of waiting transactions.

5.5 Timestamp Ordering (TO) Protocol

Every transaction Ti is assigned a unique, monotonically increasing timestamp TS(Ti) at creation. Each data item Q maintains two timestamps:

  • R-TS(Q): The largest timestamp of any transaction that successfully executed Read(Q).
  • W-TS(Q): The largest timestamp of any transaction that successfully executed Write(Q).

• Acquire Shared / Exclusive Locks
• Lock Upgrades Allowed (S → X)
• ❌ No Locks can be Released"] --> LP(("LOCK POINT
Max locks held")) LP --> S["2. Shrinking Phase (Contracting)
• Release acquired locks
• Lock Downgrades Allowed (X → S)

Basic Timestamp Ordering Rules

  • When Ti issues Read(Q):
    If TS(Ti) < W-TS(Q) → Ti is trying to read an overwritten value. Reject and Abort Ti.
    If TS(Ti) ≥ W-TS(Q) → Execute read, set R-TS(Q) = max(R-TS(Q), TS(Ti)).
  • When Ti issues Write(Q):
    If TS(Ti) < R-TS(Q) → A younger transaction already read Q. Reject and Abort Ti.
    If TS(Ti) < W-TS(Q) → An obsolete write. Reject and Abort Ti.
    Otherwise → Execute write, set W-TS(Q) = TS(Ti).

5.6 Thomas' Write Rule

Thomas' Write Rule is an optimization to Basic Timestamp Ordering for handling obsolete writes:

Modification to Write Rule

If TS(Ti) < W-TS(Q), instead of aborting Ti, IGNORE the obsolete write and let Ti continue execution!

Result: Can generate schedules that are View Serializable but NOT Conflict Serializable, significantly reducing unnecessary transaction aborts.

5.7 Validation Protocol (Optimistic Concurrency Control - OCC)

Optimistic protocols assume data conflicts are rare, delaying checking until the end of transaction execution:

Reads from DB

Test conflicting RW/WW overlaps
against active transactions"] V -->|Validation Succeeded| W["3. Write Phase
Commit updates permanently
to database disk"] V -.->|Validation Failed| A["Rollback and Restart
Discard private workspace"]
  1. Read & Execution Phase: Transaction reads values from the database and writes updates to private local workspace variables.
  2. Validation Phase: Before writing to disk, the DBMS tests if local updates conflict with concurrent transactions.
  3. Write Phase: If validation passes, local changes are committed and written permanently to disk; otherwise, the transaction aborts and restarts.

5.8 Multiple Granularity Locking (MGL)

Hierarchical locking allows transactions to lock data at different granularities (Database → Area → File → Record):

(IS / IX Intent Locks)"] --> A1["Area / Tablespace 1"] DB --> A2["Area / Tablespace 2"] A1 --> F1["File / Table 1"] A1 --> F2["File / Table 2"] F1 --> P1["Disk Page 1"] F1 --> P2["Disk Page 2"] P1 --> R1["Record / Row 1 (S / X)"] P1 --> R2["Record / Row 2 (S / X)"]
  • Intention-Shared (IS): Explicit shared lock will be placed at a finer granularity level below.
  • Intention-Exclusive (IX): Explicit exclusive lock will be placed at a finer level below.
  • Shared with Intention-Exclusive (SIX): Locks current node in Shared mode, with intention to acquire Exclusive locks below.

Worked Example 5.3: Intention Lock Propagation Path

Scenario: Transaction $T_1$ executes UPDATE Employee SET Salary = 75000 WHERE EmpID = 101. Concurrently, transaction $T_2$ executes SELECT COUNT(*) FROM Employee.

  1. T1 Lock Path (Top-Down):
    • Acquires IX on Database CorpDB
    • Acquires IX on Area HR_Data
    • Acquires IX on Table Employee
    • Acquires Exclusive (X) lock on Tuple EmpID = 101
  2. T2 Lock Request:
    • Acquires IS on Database CorpDB (Compatible with IX ✓)
    • Acquires IS on Area HR_Data (Compatible with IX ✓)
    • T2 requests Shared (S) lock on Table Employee to scan all records.
    • Conflict Check at Table Node: Table has IX held by T1. Looking at compatibility matrix, IX and S CONFLICT!
    • Result: T2 is suspended at the table root. The lock manager avoids inspecting thousands of individual records to discover the conflict!

5.9 Multi-Version Concurrency Control (MVCC)

MVCC maintains multiple physical versions of each data item. When a transaction updates an item, a new timestamped version is created rather than overwriting in place:

Key Advantage of MVCC

READERS NEVER BLOCK WRITERS, AND WRITERS NEVER BLOCK READERS!

A read query always reads the latest committed version corresponding to its start timestamp (Snapshot Isolation), completely eliminating read locks.

5.10 Storage Buffer Policies (STEAL / NO-FORCE)

Buffer Policy STEAL Policy NO-STEAL Policy
FORCE Policy Buffer manager flushes uncommitted pages (Needs UNDO). Pages flushed at commit (No REDO). Uncommitted pages never flushed (No UNDO). Flushed at commit (No REDO). High RAM cost.
NO-FORCE Policy
(Standard in modern RDBMS)		 Buffer manager flushes dirty pages before commit (Needs UNDO). Committed pages stay in RAM cache (Needs REDO). Uncommitted pages never flushed (No UNDO). Committed pages flushed asynchronously (Needs REDO).

5.11 Case Study: Oracle Concurrency Architecture

The Oracle database engine implements non-blocking multi-version concurrency control using the System Change Number (SCN) and Undo Tablespaces:

  • SGA (System Global Area): Shared memory hosting the Database Buffer Cache and Redo Log Buffer.
  • SCN (System Change Number): Logical clock counter incremented on every transaction commit.
  • Undo Segments: Reconstruct older data block images dynamically when long queries read across concurrent updates.

Root Cause: ORA-01555 Snapshot Too Old

Occurs when a long-running query needs to reconstruct past block images using undo segments, but concurrent transactions overwrite those undo blocks before the query finishes.

Resolution: Increase UNDO_RETENTION and expand UNDO TABLESPACE capacity.

Worked Example 5.5: Deadlock Prevention — Wait-Die vs Wound-Wait Decision Matrix

Suppose older transaction $T_{old}$ has timestamp $TS = 10$ and younger transaction $T_{young}$ has $TS = 50$:

Scenario Requesting Tx Holding Tx Wait-Die Scheme (Non-preemptive) Wound-Wait Scheme (Preemptive)
Case 1: Older requests from Younger Told (TS = 10) Tyoung (TS = 50) Told is ALLOWED TO WAIT.
Older transaction can wait for younger.		 Told WOUNDS Tyoung!
Younger transaction is immediately preempted, aborted, and rolled back.
Case 2: Younger requests from Older Tyoung (TS = 50) Told (TS = 10) Tyoung DIES!
Younger transaction is immediately aborted and restarted with original timestamp.		 Tyoung is ALLOWED TO WAIT.
Younger is permitted to wait for older to finish.

Deadlock Freedom Proof: In both schemes, wait edges can only point in one monotonic timestamp direction (Older → Younger in Wait-Die, Younger → Older in Wound-Wait). Thus, a directed cycle can NEVER form!
