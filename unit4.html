4.1 Transaction Concept & ACID Properties

A Transaction is a logical unit of database processing consisting of one or more database access operations (read, write, update, delete). It forms the fundamental abstraction for multi-user concurrency and crash reliability.

Property Definition & Operational Invariant Underlying DBMS Subsystem
Atomicity
(All-or-Nothing)		 A transaction is an indivisible unit of work; either all its operations execute permanently, or none are reflected in the database. Recovery Manager: Log-based recovery (Write-Ahead Logging / UNDO logs) and shadow paging.
Consistency
(Correctness)		 Execution of a transaction in isolation preserves database invariants, taking the database from one valid state to another. Integrity Subsystem: Schema DDL constraints, foreign key assertions, and triggers.
Isolation
(Independence)		 Each concurrent transaction executes as if it were the sole program running, preventing intermediate dirty state visibility. Concurrency Control Manager: Strict 2-Phase Locking (2PL), Timestamp Ordering, and MVCC.
Durability
(Survivability)		 Once committed, updates survive all subsequent hardware failures, operating system crashes, and power losses. Storage & Log Engine: Force-flushing REDO log buffers to non-volatile disk/SSD prior to commit ack.

4.3 Schedules & Conflicting Operations

A Schedule (History) S is the chronological sequence of interleaved operations across concurrent transactions.

Conditions for Conflicting Operations

Two operations I_i and I_j in schedule S belonging to transactions Ti and Tj (i ≠ j) are in conflict if and only if:

  1. They belong to different transactions (Ti ≠ Tj).
  2. They access the same data item (Q).
  3. At least one of the operations is a WRITE (W(Q)).
Op in Ti Op in Tj Status Technical Implication
Read(Q) Read(Q) No Conflict Concurrent reads are commutative and cannot modify state.
Read(Q) Write(Q) CONFLICT Order determines whether Ti sees pre- or post-update value.
Write(Q) Read(Q) CONFLICT Order determines whether Tj reads dirty or updated value.
Write(Q) Write(Q) CONFLICT Order determines which write persists in storage (Lost Update risk).

4.4 Precedence Graphs & Cycle Detection

Conflict serializability is verified by constructing a Precedence Graph (Serialization Graph) G = (V, E):

  • Vertices (V): All transactions participating in the schedule.
  • Edges (E): A directed edge Ti → Tj is added if an operation of Ti conflicts with and precedes an operation of Tj.

Serializability Theorem

A schedule S is Conflict Serializable if and only if its precedence graph G contains NO CYCLES (i.e., G is a Directed Acyclic Graph / DAG). Topological sorting of G gives the equivalent serial schedule order.

Worked Example 4.1: Precedence Graph & Conflict Serializability Trace

Problem Statement: Consider concurrent schedule $S_1$ executed by transactions $T_1$, $T_2$, and $T_3$ operating on data items $X$, $Y$, and $Z$:

S1: R1(X) → R2(Z) → R1(Z) → R3(X) → R3(Y) → W1(X) → W3(Y) → R2(Y) → W2(Z) → W2(Y)

Determine whether $S_1$ is conflict serializable. If yes, find its equivalent serial schedule order.

Step 1: Chronological Conflict Pair Analysis
Data Item Prior Operation Later Conflicting Operation Conflicting Pair Derived Directed Edge
X R3(X) (step 4) W1(X) (step 6) Read-Write (R3-W1) T3 → T1
Y W3(Y) (step 7) R2(Y) (step 8) Write-Read (W3-R2) T3 → T2
Y W3(Y) (step 7) W2(Y) (step 10) Write-Write (W3-W2) T3 → T2 (parallel edge)
Z R1(Z) (step 3) W2(Z) (step 9) Read-Write (R1-W2) T1 → T2
Step 2: Precedence Graph Edge Set & Cycle Check

The set of directed edges in precedence graph $G = (V, E)$ is:

V = {T1, T2, T3}
E = { (T3 → T1), (T3 → T2), (T1 → T2) }

graph LR T3["T3"] -->|"on X and Y"| T1["T1"] T3 -->|on Y| T2["T2"] T1 -->|on Z| T2 style T3 fill:#ecfdf5,stroke:#059669,stroke-width:2px style T1 fill:#eff6ff,stroke:#2563eb,stroke-width:2px style T2 fill:#fef3c7,stroke:#d97706,stroke-width:2px
Step 3: Topological Sort & Conclusion
  • In-degree of T3 = 0 (No incoming edges) → Execute T3 first.
  • Remove T3; in-degree of T1 becomes 0 → Execute T1 second.
  • Remove T1; in-degree of T2 becomes 0 → Execute T2 third.

Conclusion: Precedence graph contains NO CYCLES. Therefore, Schedule $S_1$ is Conflict Serializable with equivalent serial schedule order: T3 → T1 → T2.

4.5 View Serializability & Blind Writes

View serializability is a broader definition of correctness. Two schedules S and S' are View Equivalent if:

  1. For each data item Q, if Ti reads initial value of Q in S, Ti must read initial value of Q in S'.
  2. For each data item Q, if Ti reads the value written by Tj in S, Ti must read the value written by Tj in S'.
  3. For each data item Q, the transaction that performs the final write on Q in S must perform the final write in S'.

Conflict vs View Serializability

Every Conflict Serializable schedule is View Serializable. A schedule that is View Serializable but NOT Conflict Serializable must contain Blind Writes (a write operation on Q without prior read).

Worked Example 4.2: View Serializability with Blind Writes

Problem Statement: Consider schedule $S_2$ with 3 transactions accessing variable $A$:

S2: R1(A) → W2(A) → W1(A) → W3(A)

Prove that $S_2$ is NOT conflict serializable, but IS view serializable.

Part A: Conflict Serializability Analysis
  1. Operation R1(A) precedes W2(A) → Edge T1 → T2.
  2. Operation W2(A) precedes W1(A) → Edge T2 → T1.

Since there is a bidirectional cycle T1 ⇌ T2, $S_2$ is NOT Conflict Serializable.

Part B: View Serializability Test against Serial Schedule S' = T1 → T2 → T3
View Equivalence Condition In Schedule S2 In Serial S' (T1 → T2 → T3) Evaluation
1. Initial Read of A T1 reads initial value from DB T1 reads initial value from DB Matched ✓
2. Write-Read Dependencies Neither T2 nor T3 reads A Neither T2 nor T3 reads A Matched ✓ (Trivially true)
3. Final Write on A T3 executes the final write W3(A) T3 executes the final write W3(A) Matched ✓

Conclusion: $S_2$ satisfies all 3 view equivalence conditions with serial schedule T1 → T2 → T3. Thus, $S_2$ is View Serializable! The conflict cycle was benign because $W_2(A)$ was a Blind Write whose value was immediately overwritten by $W_1(A)$ without ever being read by any transaction.

4.6 Recoverability Hierarchy

In addition to serializability, a schedule must be recoverable to handle runtime transaction aborts:

  • Recoverable Schedule: If Ti writes Q and Tj subsequently reads Q, then Ti must commit before Tj commits. Prevents dirty read commit anomalies.
  • Cascadeless (Avoids Cascading Aborts - ACA): Every transaction reads ONLY values written by already committed transactions. Eliminates chained rollbacks.
  • Strict Schedule: No transaction can read OR overwrite an item Q until the transaction that previously wrote Q has committed or aborted. Simplifies recovery using simple before-image restoration.

Strict ⊆ Cascadeless ⊆ Recoverable ⊆ All Schedules

Worked Example 4.3: Comparative Trace of Recoverable, Cascadeless, and Non-Recoverable Schedules

Schedule Classification Interleaved Execution Sequence Engine Behavior & Failure Consequence
Non-Recoverable Schedule W1(A) → R2(A) → Commit2 → Abort1 Fatal Inconsistency: T2 reads dirty data from T1 and commits. When T1 subsequently aborts, T1's changes must be rolled back, but ACID Durability strictly prohibits undoing committed T2! The database becomes irrecoverably corrupt.
Recoverable, but Cascading W1(A) → R2(A) → W2(B) → R3(B) → Abort1 Cascading Abort: T2 does not commit before T1, so the schedule is recoverable. However, when T1 aborts, T2 (which read uncommitted A) must abort. This in turn forces T3 (which read B from T2) to abort, triggering a catastrophic cascading rollback.
Cascadeless (ACA) Schedule W1(A) → Commit1 → R2(A) → Commit2 Zero Cascading: T2 is suspended until T1 commits. If T1 aborts prior to commit, T2 simply reads the previous clean consistent database state. No chained aborts can ever occur.

4.7 Log Recovery & Write-Ahead Logging (WAL)

The Write-Ahead Logging (WAL) protocol guarantees atomicity and durability:

Core Rules of Write-Ahead Logging

  1. Undo Logging Rule: The before-image (old value) log record must be force-flushed to non-volatile disk storage BEFORE the modified data block is written to disk.
  2. Redo Logging Rule: All log records up to the <commit T> marker must be force-written to disk BEFORE the commit acknowledgment is returned to the user.

  3. During crash recovery, only transactions active during or starting after the most recent checkpoint need to be inspected.

4.9 Deadlock Handling & Wait-For Graphs (WFG)

Holds Lock on Z
Waits for X"] T3 -->|"Waits for X (CYCLE DETECTED)"| T1 style T1 fill:#fee2e2,stroke:#dc2626,stroke-width:2px style T2 fill:#fee2e2,stroke:#dc2626,stroke-width:2px style T3 fill:#fee2e2,stroke:#dc2626,stroke-width:2px
  • Deadlock Prevention (Timestamp based):
    • Wait-Die (Non-preemptive): Older transaction waits for younger; younger transaction dies (aborts) immediately if requesting from older.
    • Wound-Wait (Preemptive): Older transaction wounds (preempts/aborts) younger transaction holding lock; younger waits for older.
  • Deadlock Detection: Construct a directed Wait-For Graph (WFG) where vertices are active transactions and edge Ti → Tj means Ti waits for a lock held by Tj. A cycle signifies a deadlock, resolved by selecting a victim transaction to abort.

4.10 Distributed Storage & Data Fragmentation

In distributed database systems (DDBMS), relations are split across geographically separated network sites:

  • Horizontal Fragmentation: Relation is partitioned into row subsets using selection conditions (σ). Reconstructed using UNION.
  • Vertical Fragmentation: Relation is partitioned into column subsets using projection (π). Every fragment must retain the Primary Key. Reconstructed using NATURAL JOIN.
  • Mixed / Hybrid Fragmentation: Combining horizontal and vertical splitting.

4.11 Two-Phase Commit Protocol (2PC)

2PC guarantees atomic commits across multiple autonomous nodes in a distributed database system:

sequenceDiagram autonumber actor C as Coordinator Node actor P1 as Cohort Participant 1 actor P2 as Cohort Participant 2 Note over C,P2: Phase 1: Prepare (Voting) Phase C->>P1: PREPARE Message C->>P2: PREPARE Message P1-->>C: VOTE_COMMIT P2-->>C: VOTE_COMMIT Note over C,P2: Phase 2: Commit Phase C->>P1: GLOBAL_COMMIT Broadcast C->>P2: GLOBAL_COMMIT Broadcast P1-->>C: ACK P2-->>C: ACK Note over C: Transaction Successfully Committed Globally
Phase Coordinator Actions Participant Actions
Phase 1: Prepare / Voting Writes <prepare T> to log and broadcasts PREPARE message to all sites. Executes up to commit. Writes undo/redo logs. Votes VOTE_COMMIT or VOTE_ABORT.
Phase 2: Decision If all voted commit → writes <commit T>, broadcasts GLOBAL_COMMIT. If any aborted → GLOBAL_ABORT. Applies decision, writes commit/abort to local log, flushes, and returns ACK to coordinator.

4.12 Distributed Directory Systems

  • Centralized Directory: A single master server holds catalog mappings for all sites. Single point of failure.
  • Fully Replicated Directory: Entire catalog is cloned at every node, optimizing local query reads at the cost of broadcast updates.
  • Distributed Partitioned Directory: Each site maintains directory entries only for locally resident fragments.

4.13 Solved Exam Crash Recovery Replay

Worked Example 4.4: Step-by-Step WAL Log Crash Recovery Trace

Problem Statement: A DBMS uses Write-Ahead Logging (WAL) with immediate database modification and checkpointing. Consider the persistent log file on non-volatile disk shown below up to the point of an unexpected system power failure:

LSN Log Record Format Description / Action
101<T1, START>T1 begins execution
102<T1, A, 500, 450>T1 updates A from 500 to 450
103<T2, START>T2 begins execution
104<T1, COMMIT>T1 commits successfully
105<CHECKPOINT {T2}>Checkpoint: T2 is currently active in memory
106<T3, START>T3 begins execution
107<T2, B, 1000, 1200>T2 updates B from 1000 to 1200
108<T2, COMMIT>T2 commits successfully
109<T4, START>T4 begins execution
110<T3, C, 200, 350>T3 updates C from 200 to 350
SYSTEM CRASH OCCURS IMMEDIATELY AFTER LSN 110
Step 1: Construct the REDO and UNDO Transaction Lists
  • Active Transactions at Checkpoint (LSN 105): {T2}
  • Transactions Starting after Checkpoint: {T3, T4}
  • Committed Transactions:
    • T1 committed at LSN 104 (prior to checkpoint). Its modified buffer pages were flushed to disk at checkpoint; hence, no action needed for T1.
    • T2 committed at LSN 108 (after checkpoint) → Must be redone to satisfy durability! REDO_LIST = {T2}.
  • Uncommitted / In-flight Transactions at Crash:
    • T3 started at LSN 106, made changes at LSN 110, but never reached commit before the crash.
    • T4 started at LSN 109, never reached commit.
    • Hence, all uncommitted transactions must be aborted → UNDO_LIST = {T3, T4}.
Step 2: Recovery Execution Protocol
Phase Scan Direction Operations Performed
1. REDO Phase Forward (LSN 105 → LSN 110) Re-applies all modifications for transactions in REDO_LIST = {T2}:
• At LSN 107: Set B = 1200 (New Value). Guarantees durability of committed transactions.
2. UNDO Phase Backward (LSN 110 → LSN 101) Reverts all modifications for transactions in UNDO_LIST = {T3, T4}:
• At LSN 110: Restore C = 200 (Old Value / Before-Image).
• Write compensation log records (CLR) and append <T3, ABORT> and <T4, ABORT> to persistent log.
Step 3: Final Post-Recovery Database Values

A = 450 (Committed by T1) | B = 1200 (Re-applied from T2) | C = 200 (Reverted to old value)

Summary: Atomicity is preserved by rolling back uncommitted transactions T3 and T4, and Durability is preserved by redoing committed transaction T2.
