Unit I: Database Architecture, ER Modeling & Keys

3-Level ANSI/SPARC Architecture

External (View)Individual user views; abstracts away other table schemas.
Conceptual (Logical)Entire database structure: entities, attributes, constraints.
Internal (Physical)Data storage, block allocation, record formats, B-tree indexes.

Data Independence

LogicalAltering Conceptual schema without changing External views.
PhysicalAltering Physical storage without changing Conceptual schema.

ER Diagram Symbols Reference

RectangleStrong Entity Set (independent existence)
Double RectangleWeak Entity Set (depends on identifying owner)
DiamondRelationship Set
Double DiamondIdentifying Relationship for weak entity
Ellipse (Oval)Attribute
Solid UnderlinePrimary Key / Candidate Key attribute
Dashed UnderlinePartial Key (Discriminator) of Weak Entity
Double EllipseMultivalued Attribute (e.g. Phone numbers)
Dashed EllipseDerived Attribute (e.g. Age from DOB)
Double LineTotal Participation (Existence dependency)

Database Keys Hierarchy

SuperkeyAny attribute set uniquely identifying a tuple ($SK \implies \text{Unique}$).
Candidate KeyMinimal superkey (no redundant attributes; removal destroys uniqueness).
Primary KeyChosen candidate key; strictly NOT NULL and uniquely indexed.
Alternate KeyCandidate keys not chosen as the primary key.
Foreign KeyAttribute in child table referencing primary key of parent table.
Compound KeyKey composed of two or more attributes.

Key Superkey Formula

For $R(A_1, \dots, A_n)$ with candidate key of size $k$: Total superkeys = $2^{n-k}$.

Relational Integrity Constraints

Domain IntegrityAttribute values must belong to declared data type/domain range.
Entity IntegrityPrimary key cannot contain NULL values ($PK \neq \text{NULL}$).
Referential IntegrityForeign key value must equal an existing parent PK value or be NULL.
Key ConstraintNo two distinct tuples can share identical candidate key values.

FK Delete Cascade Options

ON DELETE CASCADE | SET NULL | RESTRICT | NO ACTION

Unit II: Relational Algebra & SQL Reference

Relational Algebra Core Operators

Selection $\sigma_p(R)$Horizontal slice: filters tuples satisfying predicate $p$.
Projection $\pi_{A}(R)$Vertical slice: selects attributes $A$, eliminates duplicates.
Cartesian Product $R \times S$Cross product: combines all rows ($|R| \times |S|$ tuples).
Set Union $R \cup S$Tuples in $R$ or $S$ (requires union-compatibility).
Set Difference $R - S$Tuples in $R$ but not in $S$.
Rename $\rho_{S}(R)$Renames relation $R$ to $S$ or attributes.
Natural Join $R \bowtie S$Equality on all shared column names without column duplication.
Division $R \div S$Finds tuples in $R$ associated with ALL tuples in $S$.

SQL Command Categories

DDLCREATE, ALTER, DROP, TRUNCATE (Auto-committed)
DMLSELECT, INSERT, UPDATE, DELETE (Requires commit)
DCLGRANT, REVOKE (Privilege security management)
TCLCOMMIT, ROLLBACK, SAVEPOINT, SET TRANSACTION

TRUNCATE vs DELETE

TRUNCATEDDL, deallocates pages, resets identity, faster, no WHERE.
DELETEDML, row-by-row logged, preserves space, supports WHERE.

SQL Joins Quick Summary

INNER JOINReturns only rows with matches in BOTH tables.
LEFT JOINALL rows from left table + matched rows from right table (NULL padded).
RIGHT JOINALL rows from right table + matched rows from left table (NULL padded).
FULL OUTER JOINALL rows when there is a match in either left or right table.
CROSS JOINCartesian product of both tables.
SELECT e.name, d.dept_name FROM Employee e LEFT JOIN Department d ON e.dept_id = d.dept_id;

Aggregation, GROUP BY & HAVING

AggregatesCOUNT(), SUM(), AVG(), MIN(), MAX()
WHERE vs HAVINGWHERE filters individual rows; HAVING filters grouped rows.
Query ExecutionFROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
SELECT dept_id, AVG(salary) AS avg_sal FROM Employee WHERE status = 'ACTIVE' GROUP BY dept_id HAVING AVG(salary) > 50000 ORDER BY avg_sal DESC;

Unit III: Normalization & Functional Dependencies

Armstrong's Axioms & Inference Rules

Primary Axioms (Sound & Complete)

ReflexivityIf $Y \subseteq X$, then $X \to Y$.
AugmentationIf $X \to Y$, then $XZ \to YZ$.
TransitivityIf $X \to Y$ and $Y \to Z$, then $X \to Z$.

Secondary Derived Rules

Union$X \to Y \land X \to Z \implies X \to YZ$
Decomposition$X \to YZ \implies X \to Y \land X \to Z$
Pseudo-transitivity$X \to Y \land \gamma Y \to Z \implies \gamma X \to Z$

Normal Forms Summary (1NF to BCNF)

1NFAll attribute values atomic; no repeating groups or multivalued arrays.
2NFIn 1NF + NO partial dependencies (non-prime dependent on proper subset of candidate key).
3NFIn 2NF + For every $X \to A$, either $X$ is a superkey OR $A$ is prime attribute.
BCNFStrict: For every non-trivial $X \to A$, $X$ MUST strictly be a superkey.
4NFIn BCNF + No non-trivial Multivalued Dependencies ($\alpha \twoheadrightarrow \beta$).
5NFIn 4NF + No Join Dependencies not implied by candidate keys.

Attribute Closure Algorithm ($X^+$)

Algorithm Steps

  1. Initialize: $X^{(0)} = X$.
  2. Repeat: For each FD $Y \to Z \in F$, if $Y \subseteq X^{(i)}$, then $X^{(i+1)} = X^{(i)} \cup Z$.
  3. Stop when $X^{(i+1)} = X^{(i)}$. Output $X^+ = X^{(i)}$.

Key Testing Rule

If $X^+$ contains ALL attributes of relation $R$, then $X$ is a Superkey. If no proper subset of $X$ covers $R$, $X$ is a Candidate Key.

Decomposition Properties

Lossless Join Test (2 Sub-relations)

$R = R_1 \cup R_2$ is Lossless Join if and only if:

(R1 ∩ R2) → R1 OR (R1 ∩ R2) → R2

Dependency Preservation

$(F_1 \cup F_2)^+ = F^+$

3NF vs BCNF Guarantee

3NFGuaranteed Lossless Join + Dependency Preserving.
BCNFGuaranteed Lossless Join; may NOT preserve dependencies.

Unit IV: Transactions & Serializability

ACID Properties & Subsystems

AtomicityAll or Nothing execution (Recovery Manager & UNDO logs).
ConsistencyPreserves schema integrity constraints & invariant balances.
IsolationConcurrent executions do not cross-contaminate (Concurrency Controller).
DurabilityCommitted changes survive system crashes (WAL log & REDO lists).

Conflict Serializability Test

Conflicting Operations

Two operations conflict iff they are from different transactions, access the SAME data item, and at least ONE is a WRITE ($R_1(A)-W_2(A)$, $W_1(A)-R_2(A)$, $W_1(A)-W_2(A)$).

Precedence Graph Rule

  • Draw edge $T_i \to T_j$ if $T_i$ performs conflicting op before $T_j$.
  • Acyclic Graph ⇔ Schedule is Conflict Serializable.
  • Topological sort gives equivalent serial schedule order.

Schedule Classes Hierarchy

Serial ⊂ Strict ⊂ Cascadeless (ACA) ⊂ Recoverable
RecoverableIf $T_j$ reads $X$ written by $T_i$, then $T_i$ must commit before $T_j$ commits.
CascadelessTransactions only read COMMITTED values of data items.
StrictTransactions neither read NOR write $X$ until the writer commits/aborts.

Concurrency Anomalies & Isolation

Dirty Read (G1)$T_1$ reads uncommitted value written by $T_2$ which later aborts.
Non-Repeatable Read (G2)$T_1$ reads row, $T_2$ updates/deletes it, $T_1$ re-reads different data.
Phantom Read (A3)$T_1$ reads range, $T_2$ inserts matching rows, $T_1$ re-reads extra rows.
Lost Update$T_1$ and $T_2$ overwrite each other's changes without seeing updates.

Unit V: Concurrency Control, Deadlocks & Recovery

Lock Modes & Two-Phase Locking (2PL)

Lock Compatibility Matrix

Requested \ HeldShared (S)Exclusive (X)
Shared (S)GrantedBlocked
Exclusive (X)BlockedBlocked

2PL Rule

Growing Phase: Locks acquired, none released. Shrinking Phase: Locks released, none acquired. Guarantees Serializability, but NOT deadlock-free.

Strict vs Rigorous 2PL

Strict 2PLHold ALL Exclusive (X) locks until Commit/Abort.
Rigorous 2PLHold ALL locks (both S and X) until Commit/Abort.

Deadlock Prevention Schemes

Timestamp Prevention ($TS(T_i) < TS(T_j) \implies T_i \text{ is Older}$)

Wait-Die (Non-preemptive)If $T_{old}$ requests lock held by $T_{young}$ → $T_{old}$ Waits.
If $T_{young}$ requests lock held by $T_{old}$ → $T_{young}$ Dies (Aborts).
Wound-Wait (Preemptive)If $T_{old}$ requests lock held by $T_{young}$ → $T_{old}$ Wounds (Preempts/Aborts) $T_{young}$.
If $T_{young}$ requests lock held by $T_{old}$ → $T_{young}$ Waits.

Deadlock Detection

Wait-For Graph (WFG) cycle detection algorithm $O(V+E)$. Victim selected based on minimum rollback cost.

Timestamp Ordering & Thomas Rule

Read Operation Rule for $T_i$ on $Q$

  • If $TS(T_i) < W\text{-}TS(Q)$ → Abort and restart $T_i$.
  • Else → Execute $R(Q)$, set $R\text{-}TS(Q) = \max(R\text{-}TS(Q), TS(T_i))$.

Write Operation Rule for $T_i$ on $Q$

  • If $TS(T_i) < R\text{-}TS(Q)$ → Abort and restart $T_i$.
  • If $TS(T_i) < W\text{-}TS(Q)$ → Standard TS: Abort $T_i$. Thomas Write Rule: Ignore write! (Obsolete).
  • Else → Execute $W(Q)$, set $W\text{-}TS(Q) = TS(T_i)$.

Log-Based Recovery & Checkpointing

Write-Ahead Logging (WAL) Protocol

Log record reflecting an update must be flushed to stable storage BEFORE the dirty data page is written to database disk.

Crash Recovery Rules from Checkpoint

REDO ListTransactions with both <Ti start> and <Ti commit> in log. Replay writes forward.
UNDO ListTransactions with <Ti start> but NO <Ti commit> at crash. Roll back changes backward.

Immediate vs Deferred Update

Immediate: Requires both UNDO and REDO. Deferred: Updates kept in cache until commit; requires REDO only (never UNDO).
